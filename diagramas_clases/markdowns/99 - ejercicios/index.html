    Ejercicios de diagramas de clases

    Estos doce ejercicios son las actividades de la unidad: en todos, la solución es un diagrama de clases construido a partir de un enunciado. Lo que cambia de uno a otro es el dominio del problema y el número de decisiones de modelado que hay que tomar: desde una biblioteca con préstamos hasta un holding con relaciones ternarias.

    Cómo se resuelven

    Se pueden dibujar a mano y comprobar después con Dia, que es la herramienta del apartado teórico. Las soluciones de esta página usan Mermaid para que el diagrama se pueda leer aquí mismo, pero la notación es la misma: cajas con tres compartimentos, flechas de herencia con punta triangular hueca, rombos para la agregación y la composición, y multiplicidades en los extremos.

    1. Biblioteca con copias y préstamos

    Diseña el siguiente diagrama de clases:

    • Una biblioteca tiene copias de libros. Estos últimos se caracterizan por su nombre, tipo (novela, teatro, poesía, ensayo), editorial, año y autor.
    • Los autores se caracterizan por su nombre, nacionalidad y fecha de nacimiento.
    • Cada copia tiene un identificador, y puede estar en la biblioteca, prestada, con retraso o en reparación.
    • Los lectores pueden tener un máximo de 3 libros en préstamo.
    • Cada libro se presta un máximo de 30 días; por cada día de retraso, se impone una "multa" de dos días sin posibilidad de coger un nuevo libro.
    • Realiza un diagrama de clases y añade los métodos necesarios para realizar el préstamo y devolución de libros.
    classDiagram
    class Libro {
        -nombre : String
        -tipo : TipoLibro
        -editorial : String
        -anio : int
    }
    class Autor {
        -nombre : String
        -nacionalidad : String
        -fechaNacimiento : Date
    }
    class Copia {
        -identificador : String
        -estado : EstadoCopia
    }
    class Lector {
        -numeroSocio : String
        +prestar(c : Copia) boolean
        +devolver(c : Copia) double
    }
    class Prestamo {
        -fechaInicio : Date
        -fechaEntrega : Date
        +diasRetraso() int
        +diasSancion() int
    }
    Libro "1..*" -- "1..*" Autor : escrito por
    Libro "1" -- "1..*" Copia : del libro
    Lector "1" -- "*" Copia : solicita
    Prestamo .. Lector
    Prestamo .. Copia

    La decisión que cambia el modelo es separar libro de copia. El libro es la obra (El Quijote), y la copia es el ejemplar físico con su identificador; la biblioteca presta copias, no obras, y por eso el préstamo cuelga de Copia. Si se hubiera puesto el estado en Libro, no se podría tener a la vez un ejemplar prestado y otro en la estantería.

    El préstamo se modela como clase asociativa entre Lector y Copia, porque las fechas y la sanción no pertenecen a ninguno de los dos. Los métodos prestar() y devolver() van en Lector, que es quien conoce sus préstamos; devolver() devuelve la multa calculada. Las dos restricciones del enunciado, tres libros como máximo y treinta días de plazo, no se dibujan: se documentan en el diagrama y se comprueban en esos métodos.

    2. Empresas, empleados y clientes

    Representa mediante un diagrama de clases la siguiente especificación:

    • Una aplicación necesita almacenar información sobre empresas, sus empleados y sus clientes. Ambos se caracterizan por su nombre y edad.
    • Los empleados tienen un sueldo bruto; los empleados que son directivos tienen una categoría, así como un conjunto de empleados subordinados.
    • De los clientes además se necesita conocer su teléfono de contacto.
    • La aplicación necesita mostrar los datos de empleados y clientes.
    classDiagram
    class Persona {
        <<abstract>>
        #nombre : String
        #edad : int
        +mostrarDatos() String
    }
    class Empleado {
        -sueldoBruto : double
    }
    class Directivo {
        -categoria : String
    }
    class Cliente {
        -telefono : String
    }
    class Empresa {
        -nombre : String
    }
    Persona <|-- Empleado
    Persona <|-- Cliente
    Empleado <|-- Directivo
    Directivo "0..1" --> "*" Empleado : subordina
    Empresa "1" *-- "1..*" Empleado : emplea
    Empresa "1" o-- "*" Cliente : atiende

    Persona se declara abstracta porque reúne lo común (nombre, edad y mostrarDatos()) pero en la aplicación no existe una persona suelta: o es empleado o es cliente. La jerarquía evita repetir los dos atributos y permite que el código trate a ambos con una sola variable de tipo Persona.

    El directivo no es un tipo paralelo de empleado, sino un empleado con categoría y con subordinados; de ahí que herede de Empleado y que tenga una asociación consigo mismo. Esa asociación reflexiva con 0..1 en el extremo del jefe dice que un empleado puede no tener a nadie a su cargo, y el * del otro extremo, que un mando puede tener varios.

    3. Gestión de pedidos

    Realiza el diseño de una aplicación para la gestión de pedidos. La aplicación deberá:

    • Manejar clientes (se guarda su nombre, dirección, teléfono y e-mail), que pueden realizar pedidos de productos, de los cuales se anota la cantidad en stock. Un cliente puede tener una o varias cuentas para el pago de los pedidos. Cada cuenta está asociada a una tarjeta de crédito, y tiene una cierta cantidad disponible de dinero, que el cliente debe aumentar periódicamente para poder realizar nuevos pedidos.
    • Un cliente puede empezar a realizar un pedido sólo si tiene alguna cuenta con dinero disponible. Al realizar un pedido, un cliente puede agruparlos en pedidos simples o compuestos. Los pedidos simples están asociados a una sola cuenta de pago y (por restricciones en la distribución) contienen un máximo de 20 unidades del mismo o distinto tipo de producto. A su vez, un pedido compuesto contiene dos o más pedidos, que pueden ser simples o compuestos. El sistema debe garantizar que todos los pedidos simples que componen un pedido compuesto se paguen con cuentas del mismo cliente. Además, sólo es posible realizar peticiones de productos en stock.
    • Existe una clase (de la cual debe haber una única instancia en la aplicación) responsable del cobro, orden de distribución y confirmación de los pedidos. El cobro de los pedidos se hace una vez al día, y el proceso consiste en comprobar todos los pedidos pendientes de cobro, y cobrarlos de la cuenta de pago correspondiente. Si una cuenta no tiene suficiente dinero, el pedido se rechaza (si es parte de un pedido compuesto, se rechaza el pedido entero). Una vez que el pedido está listo para servirse, se ordena su distribución, y una vez entregado, pasa a estar confirmado.
    classDiagram
    class Cliente {
        -nombre : String
        -direccion : String
        -telefono : String
        -email : String
        +puedePedir() boolean
    }
    class CuentaPago {
        -saldoDisponible : double
        +tieneSaldo(importe : double) boolean
    }
    class TarjetaCredito {
        -numero : String
        -titular : String
        -caducidad : Date
    }
    class Pedido {
        <<abstract>>
        -numero : int
        -fecha : Date
        -estado : EstadoPedido
        -precioTotal : double
        +cobrar() boolean
    }
    class PedidoSimple {
        -unidadesTotales : int
    }
    class PedidoCompuesto
    class LineaPedido {
        -cantidad : int
    }
    class Producto {
        -codigo : String
        -nombre : String
        -precio : double
        -stock : int
    }
    class GestorPedidos {
        <<singleton>>
        +cobrarPendientes() void
        +ordenarDistribucion() void
        +confirmarEntrega(p : Pedido) void

    Cliente "1" --> "1..*" CuentaPago : posee
    CuentaPago "1" -- "1" TarjetaCredito : asociada
    Cliente "1" --> "*" Pedido : realiza
    Pedido <|-- PedidoSimple
    Pedido <|-- PedidoCompuesto
    PedidoCompuesto "1" *-- "2..*" Pedido : agrupa
    PedidoSimple "1" *-- "1..*" LineaPedido : contiene
    LineaPedido "*" --> "1" Producto : referencia
    PedidoSimple "*" --> "1" CuentaPago : paga con
    GestorPedidos ..> Pedido : cobra y distribuye

    El patrón compuesto aparece en la jerarquía de pedidos: PedidoCompuesto contiene dos o más Pedido, que pueden ser simples o compuestos a su vez. Ese 2..* contra la clase abstracta es lo que permite anidar pedidos sin límite y, a la vez, obliga a que un compuesto nunca esté vacío.

    Las líneas de pedido son las que llevan la cantidad de cada producto, y de ahí sale la restricción de veinte unidades: el total de la línea se controla en PedidoSimple. La condición de que todos los pedidos simples de un compuesto se paguen con cuentas del mismo cliente no se puede dibujar con una multiplicidad, así que se documenta como restricción del modelo y se comprueba en cobrar().

    GestorPedidos lleva el estereotipo <<singleton>> porque el enunciado pide una única instancia; es el encargado de recorrer los pedidos pendientes, cobrarlos y rechazar el compuesto entero cuando una cuenta no tiene saldo.

    4. Estudio de arquitectura

    Un estudio de arquitectura desea crear una base de datos para gestionar sus proyectos:

    • Cada proyecto tiene un código y un nombre. Un proyecto tiene uno y solo un jefe de proyecto, y un jefe de proyecto sólo puede estar involucrado en un proyecto o en ninguno.
    • De cada jefe de proyecto se desean recoger sus datos personales (código, nombre, dirección y teléfono). Un jefe de proyecto se identifica por un código. No hay dos jefes de proyecto con el mismo nombre.
    • Un proyecto se compone de una serie de planos, pero éstos se quieren guardar de modo independiente al proyecto: si se dejara de trabajar en un proyecto, se desea mantener la información de los planos asociados.
    • De los planos se desea guardar su número de identificación, la fecha de entrega, los arquitectos que trabajan en él y un dibujo del plano general con información acerca del número de figuras que contiene.
    • Los planos tienen figuras. De cada figura se desea conocer el identificador, el nombre, el color, el área y el perímetro. Además, de los polígonos se desea conocer el número de líneas que tienen. El perímetro se desea que sea un método diferido; el área se desea implementarla como genérica para cualquier tipo de figura, pero además se desea un método específico para el cálculo del perímetro de los polígonos.
    • De cada línea que forma parte de un polígono se desea conocer el punto de origen y el de fin (según sus coordenadas X e Y), así como la longitud. Cada línea tiene un identificador que permite diferenciarla del resto. La longitud de la línea se puede calcular a partir de sus puntos de origen y final.
    classDiagram
    class Proyecto {
        -codigo : String
        -nombre : String
    }
    class JefeProyecto {
        -codigo : String
        -nombre : String
        -direccion : String
        -telefono : String
    }
    class Plano {
        -numeroIdentificacion : String
        -fechaEntrega : Date
        -dibujo : String
    }
    class Arquitecto {
        -codigo : String
        -nombre : String
    }
    class Figura {
        <<abstract>>
        #identificador : String
        #nombre : String
        #color : String
        +area() double
        +perimetro() double
    }
    class Poligono {
        -numeroLineas : int
        +perimetro() double
    }
    class Linea {
        -identificador : String
        +longitud() double
    }
    class Punto {
        -x : double
        -y : double
    }
    JefeProyecto "0..1" -- "1" Proyecto : dirige
    Proyecto "1" o-- "*" Plano : agrupa
    Arquitecto "*" -- "*" Plano : trabaja en
    Plano "1" *-- "1..*" Figura : contiene
    Figura <|-- Poligono
    Poligono "1" *-- "3..*" Linea : formado por
    Linea "1" *-- "1" Punto : origen
    Linea "1" *-- "1" Punto : fin

    La relación entre Proyecto y Plano es una agregación, no una composición, y ese es el detalle que exige el enunciado: si se abandona el proyecto, los planos siguen existiendo. El rombo vacío del lado del proyecto lo dice, y la multiplicidad * permite que un plano quede sin proyecto asignado.

    Figura declara area() concreta y perimetro() diferida: el área se puede calcular igual para cualquier figura con los datos que ya tiene, mientras que el perímetro depende de la forma. Poligono sobrescribe perimetro() y añade el número de líneas. La línea se compone de dos Punto, que es la forma limpia de guardar las coordenadas y de calcular la longitud sin repetir campos.

    5. Redes de ordenadores

    Especificar un diagrama de clases que describa redes de ordenadores.

    • Los elementos que se pueden incluir en la red son: servidor, PC, impresora, hub y cable de red.
    • Los PCs pueden conectarse con un único hub; los servidores, con uno o varios.
    • Los servidores y PCs pueden generar mensajes, con una cierta longitud.
    • Los hubs tienen un número de puertos, algunos de los cuales pueden usarse para conectar con otros hubs.
    • Los hubs tienen cierta probabilidad de "perder" mensajes.
    • Las impresoras pueden averiarse, con cierta probabilidad, durante cierto tiempo.
    classDiagram
    class ElementoRed {
        <<abstract>>
        #identificador : String
    }
    class Servidor {
        -modelo : String
    }
    class PC {
        -modelo : String
    }
    class Impresora {
        -modelo : String
        -probabilidadAveria : double
        -tiempoAveria : int
    }
    class Hub {
        -numeroPuertos : int
        -probabilidadPerdida : double
    }
    class Cable {
        -longitud : double
    }
    class Mensaje {
        -longitud : int
        -contenido : String
    }
    ElementoRed <|-- Servidor
    ElementoRed <|-- PC
    ElementoRed <|-- Impresora
    ElementoRed <|-- Hub
    PC "1" --> "1" Hub : conecta
    Servidor "1" --> "1..*" Hub : conecta
    Hub "1" --> "0..*" Hub : interconecta
    Hub "1" *-- "1..*" Cable : usa
    Servidor "1" --> "*" Mensaje : genera
    PC "1" --> "*" Mensaje : genera
    Hub ..> Mensaje : pierde

    La clase abstracta ElementoRed recoge lo único que comparten todos los elementos, el identificador, y deja que cada uno añada lo suyo. Esa jerarquía permite tratar la red como una lista de elementos sin preguntar de qué tipo son.

    Las dos multiplicidades que pide el enunciado quedan así: un PC con 1 hub y un servidor con 1..*. La interconexión entre hubs es una asociación reflexiva, porque un hub puede usar algunos de sus puertos para colgar de otro. Los mensajes se asocian a quien los genera, y la probabilidad de pérdida se modela como atributo del hub, no como una relación: no es un objeto, es un valor que modifica su comportamiento.

    6. Alquiler de automóviles

    Se desea diseñar un diagrama de clases sobre la información de las reservas de una empresa dedicada al alquiler de automóviles:

    • Un determinado cliente puede tener en un momento dado hechas varias reservas.
    • De cada cliente se desean almacenar su DNI, nombre, dirección y teléfono. Además, dos clientes se diferencian por un código único.
    • Cada cliente puede ser avalado por otro cliente de la empresa.
    • Una reserva la realiza un único cliente, pero puede involucrar varios coches.
    • Es importante registrar la fecha de inicio y final de la reserva, el precio del alquiler de cada uno de los coches, los litros de gasolina en el depósito en el momento de realizar la reserva, el precio total de la reserva y un indicador de si el coche o los coches han sido entregados.
    • Todo coche tiene siempre asignado un determinado garaje que no puede cambiar. De cada coche se requiere la matrícula, el modelo, el color y la marca.
    • Cada reserva se realiza en una determinada agencia.

        -direccion : String
        -telefono : String
    }
    class Reserva {
        -fechaInicio : Date
        -fechaFin : Date
        -precioTotal : double
        -entregado : boolean
        +cerrar() void
    }
    class AlquilerCoche {
        -precio : double
        -litrosDeposito : double
    }
    class Coche {
        -matricula : String
        -modelo : String
        -color : String
        -marca : String
    }
    class Garaje {
        -codigo : String
        -direccion : String
    }
    class Agencia {
        -codigo : String
        -direccion : String
    }
    Cliente "0..1" --> "*" Cliente : avala
    Cliente "1" --> "*" Reserva : realiza
    Agencia "1" --> "*" Reserva : formaliza
    Reserva "1" -- "1..*" Coche : incluye
    AlquilerCoche .. Reserva
    AlquilerCoche .. Coche
    Coche "*" --> "1" Garaje : guarda en

    El precio de cada coche y los litros del depósito no son datos de la reserva ni del coche, sino del vínculo entre ambos: la misma reserva puede llevar tres coches con precios distintos, y el mismo coche cambia de depósito en cada alquiler. Por eso se modelan como clase asociativa AlquilerCoche.

    La matrícula identifica al coche y el garaje es fijo, así que la relación con Garaje es una asociación simple con 1 en el extremo del garaje, no una agregación. Y el aval es una asociación reflexiva en Cliente con 0..1 en el extremo del avalista: un cliente puede no estar avalado, pero no puede avalarse a sí mismo ni tener dos avalistas.

    7. El zoo

    Un zoo necesita una aplicación informática para llevar su organización respecto a las especies que posee, los empleados (cuidadores y guías) y los distintos itinerarios de visita que ofrece:

    • Especies: interesa el nombre en español, el nombre científico y una descripción general. Una especie puede vivir en diferentes hábitats naturales y un hábitat puede ser ocupado por diferentes especies. Las especies se encuentran en distintas zonas del parque, de manera que cada especie está en una zona y en una zona hay varias especies.
    • Hábitats: vienen definidos por el nombre, el clima y el tipo de vegetación predominantes, así como el continente o continentes en los que se encuentran.
    • Zonas: vienen definidas por el nombre y la extensión que ocupan.
    • Itinerarios: discurren por distintas zonas del parque. Interesa el código de itinerario, la duración del recorrido, la longitud, el máximo número de visitantes autorizado y el número de distintas especies que visita. Un itinerario recorre distintas zonas y una zona puede ser recorrida por diferentes itinerarios.
    • Guías: definidos por el nombre, dirección, teléfono y fecha en la que comenzaron a trabajar en el zoo. Interesa saber qué guías llevan qué itinerarios, teniendo en cuenta que un guía puede llevar varios itinerarios y que un itinerario puede ser asignado a diferentes guías en diferentes horas, siendo éstas un dato de interés.
    • Cuidadores: definidos por el nombre, dirección, teléfono y fecha de ingreso. Un cuidador puede estar a cargo de varias especies y una especie puede ser atendida por varios cuidadores, siendo de interés la fecha en la que un cuidador se hace cargo de una especie.

    }

    El zoo concentra casi todos los casos interesantes de multiplicidad. La especie se relaciona con el hábitat en muchos a muchos, porque una especie puede vivir en varios hábitats y un hábitat acoge varias especies; en cambio, con la zona es 1 a *, porque el enunciado dice que cada especie está en una sola zona.

    Hay dos clases asociativas. La primera, AsignacionGuia, guarda la hora: un guía lleva varios itinerarios, y un itinerario puede tener guías distintos a horas distintas, así que ni la hora va en el guía ni en el itinerario. La segunda, CuidadoEspecie, guarda la fecha en la que un cuidador se hace cargo de una especie, dato que tampoco pertenece a ninguno de los dos por separado.

    Los guías y los cuidadores comparten atributos, pero no se han unificado en una clase común porque en el enunciado no se pide intercambiarlos: son dos roles con relaciones distintas. Unificarlos obligaría a crear una jerarquía que después no se usa.

    8. Agencia de viajes

    Una cadena de agencias de viajes desea disponer de una base de datos con información relativa al hospedaje y vuelos de los turistas que la contratan:

    • La cadena está compuesta por un conjunto de sucursales, definidas por el código de sucursal, dirección y teléfono.
    • La cadena tiene contratados una serie de hoteles de forma exclusiva, definidos por el código de hotel, nombre, dirección, ciudad, teléfono y número de plazas disponibles.
    • También tiene contratados vuelos regulares de forma exclusiva, definidos por el número de vuelo, fecha y hora, origen y destino, plazas totales y plazas de clase turista.
    • De cada turista se almacena el código, nombre y apellidos, dirección y teléfono.
    • A la cadena le interesa conocer qué sucursal ha contratado al turista.
    • Al viajar, el turista puede elegir cualquiera de los vuelos que ofrece la cadena, y en qué clase (turista o primera) desea viajar.
    • El turista puede hospedarse en cualquiera de los hoteles que ofrece la cadena, y elegir el régimen de hospedaje (media pensión o pensión completa), siendo significativa la fecha de llegada y de partida.

    Estancia .. Hotel
    Turista "1" -- "*" Vuelo : vuela
    Billete .. Turista
    Billete .. Vuelo

    El enunciado esconde dos clases asociativas. El régimen de hospedaje y las fechas de llegada y partida dependen de la pareja turista-hotel, no de ninguno de los dos: el mismo hotel recibe a muchos turistas con fechas y regímenes distintos. Lo mismo ocurre con la clase del billete, que depende del turista y del vuelo.

    La sucursal se asocia al turista con 1 en el extremo de la sucursal, porque cada turista se contrata en una sola, mientras que una sucursal atiende a muchos. Los hoteles y los vuelos cuelgan directamente del turista porque la cadena los tiene contratados en exclusiva; no hace falta una clase intermedia que los agrupe.

    9. Control del servicio militar

    El Ministerio de Defensa desea diseñar una base de datos para llevar un cierto control de los soldados que realizan el servicio militar:

    • Un soldado se define por su código (único), su nombre y apellidos, y su graduación.
    • Existen varios cuarteles, cada uno definido por su código, nombre y ubicación.
    • Existen diferentes cuerpos del ejército (Infantería, Artillería, Armada…), y cada uno se define por un código de cuerpo y denominación.
    • Los soldados están agrupados en compañías, siendo significativos para cada una el número de compañía y la actividad principal que realiza.
    • Se desea controlar los servicios que realizan los soldados (guardias, imaginarias, cuarteleros…), definidos por el código de servicio y descripción.
    • Un soldado pertenece a un único cuerpo y a una única compañía, durante todo el servicio militar. A una compañía pueden pertenecer soldados de diferentes cuerpos, no habiendo relación directa entre compañías y cuerpos.
    • Los soldados de una misma compañía pueden estar destinados en diferentes cuarteles: una compañía puede estar ubicada en varios cuarteles, y en un cuartel puede haber varias compañías. Un soldado sólo está en un cuartel.
    • Un soldado realiza varios servicios a lo largo de la milicia. Un mismo servicio puede ser realizado por más de un soldado (con independencia de la compañía), siendo significativa la fecha de realización.

    El enunciado insiste en tres pertenencias del soldado, y las tres son asociaciones simples con 1 en el extremo contrario: un cuerpo, una compañía y un cuartel. La compañía, en cambio, se relaciona con los cuarteles en muchos a muchos, y eso es lo que permite que soldados de la misma compañía estén repartidos por cuarteles distintos.

    Los servicios son el caso de la clase asociativa: la fecha no es del soldado ni del servicio, sino de la realización concreta de ese servicio por ese soldado. Además, el enunciado aclara que no hay relación directa entre compañías y cuerpos, así que esa asociación no se dibuja: la única relación entre ambos pasa por los soldados.

    10. Seguridad en entidades bancarias

    La policía quiere crear una base de datos sobre la seguridad en algunas entidades bancarias:

    • Cada entidad bancaria se caracteriza por un código y por el domicilio de su central.
    • Cada entidad tiene más de una sucursal, caracterizada por un código y por el domicilio, así como por el número de empleados.
    • Cada sucursal contrata, según el día, algunos vigilantes jurados, que se caracterizan por un código y su edad. Un vigilante puede ser contratado por diferentes sucursales (incluso de diferentes entidades), en distintas fechas, y es un dato de interés dicha fecha, así como si se ha contratado con arma o no.
    • Se quiere controlar a las personas que han sido detenidas por atracar las sucursales. Estas personas se definen por una clave y su nombre completo.
    • Alguna de estas personas está integrada en algunas bandas organizadas, y se desea saber a qué banda pertenecen. Las bandas se definen por un número de banda y por el número de miembros.
    • Es interesante saber en qué fecha ha atracado cada persona una sucursal. Una persona puede atracar varias sucursales en diferentes fechas, y una sucursal puede ser atracada por varias personas.
    • Se quiere saber qué juez ha estado encargado del caso, sabiendo que un individuo, por diferentes delitos, puede ser juzgado por diferentes jueces. Es de interés saber, en cada delito, si la persona detenida ha sido condenada o no y, de haberlo sido, cuánto tiempo pasará en la cárcel. Un juez se caracteriza por una clave interna del juzgado, su nombre y los años de servicio.

    11. El holding de empresas

    Un holding de empresas desea tener una base de datos referente a las empresas que posee, sus vendedores y los asesores que trabajan en el holding:

    • Los vendedores se organizan en una jerarquía de pirámide: cada vendedor puede captar otros vendedores, de manera que un vendedor tendrá a su cargo varios vendedores. Un vendedor sólo podrá trabajar en una empresa y sólo podrá captar vendedores para la empresa en que trabaja, siendo importante almacenar la fecha en que se realiza la captación. Los datos de interés son el código de vendedor, nombre y dirección.
    • Las empresas cubren diferentes áreas del mercado y una misma área puede ser cubierta por varias empresas. Es interesante conocer el nombre del área y una descripción. Las empresas pueden estar actuando en varios países y en un país pueden estar actuando varias empresas. Sin embargo, cada empresa tendrá su sede en un único país, siendo importante la ciudad donde se localiza. Por cuestiones fiscales, una empresa puede tener su sede en un país en el que no esté desarrollando actividad alguna. Los datos de interés para las empresas son el nombre, la fecha de entrada en el holding, la facturación anual y el número de vendedores.
    • Los datos de interés de los países son el nombre, el PIB, el número de habitantes y la capital.
    • Los asesores entran en el holding para dar soporte en cada una de las áreas en las que actúa. Un asesor puede cubrir varias áreas y un área puede ser cubierta por varios asesores. Un asesor puede asesorar a varias empresas y una empresa tener varios asesores. Es importante saber en qué fecha un asesor comienza a trabajar para una empresa en un área determinada. Los datos de interés de los asesores son el código, nombre, dirección y titulación.

    La sede y la actividad son dos relaciones distintas entre empresa y país, y por eso aparecen dos veces en el diagrama: una con 1 (sede única, aunque sea un país donde no opera) y otra con * a * (actividad en varios países).     12. El club náutico

    Un club náutico desea tener informatizados los datos correspondientes a sus instalaciones, empleados, socios y embarcaciones:

    • Los socios vienen definidos por su nombre, dirección, DNI, teléfono y fecha de ingreso en el club.
    • Las embarcaciones vienen definidas por matrícula, nombre, tipo y dimensiones.
    • Los amarres tienen como datos de interés el número de amarre, la lectura del contador de agua y luz, y si tienen o no servicios de mantenimiento contratados.
    • Una embarcación pertenece a un socio, aunque un socio puede tener varias embarcaciones. Una embarcación ocupará un amarre y un amarre está ocupado por una sola embarcación. Es importante la fecha en la que una embarcación es asignada a un amarre.
    • Los socios pueden ser propietarios de amarres, siendo importante la fecha de compra. Un amarre pertenece a un solo socio. No hay ninguna relación directa entre la fecha en la que se compra un amarre y la fecha en la que una embarcación se asigna a un amarre.
    • El club está dividido en varias zonas definidas por una letra, el tipo de barcos que tiene, el número de barcos que contiene, la profundidad y el ancho de los amarres. Una zona tendrá varios amarres y un amarre pertenece a una sola zona.
    • Los empleados vienen definidos por su código, nombre, dirección, teléfono y especialidad. Un empleado está asignado a varias zonas y en una zona puede haber más de un empleado, siendo de interés el número de barcos de los que se encarga en cada zona. Un empleado puede no encargarse de todos los barcos de una zona.

    El club tiene tres fechas que no se pueden mezclar, y ese es el objetivo del ejercicio. La primera es la de compra del amarre por parte del socio (Propiedad); la segunda, la de asignación de una embarcación al amarre (Ocupacion); y el enunciado avisa de que no tienen por qué coincidir. La tercera es la de ingreso del socio, que es un atributo suyo y no una relación.

    La asignación del empleado a la zona lleva el número de barcos de los que se encarga, y por eso es una clase asociativa: el dato depende de la pareja empleado-zona. La zona compone sus amarres con rombo relleno, porque un amarre no existe fuera de una zona del club.

    Las dos relaciones entre socio y amarre son distintas y por eso hay dos: una es la propiedad (1 a *, con fecha de compra) y otra es el uso que hace la embarcación del amarre, que pasa por Embarcacion y no por el socio.
