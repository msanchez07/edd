    Ejercicios de diagramas de clases

    Estos ejercicios recorren los seis criterios de evaluación del bloque: identificar los conceptos de la orientación a objetos, interpretar un diagrama de clases, trazarlo a partir de un enunciado, generar código desde el modelo y obtener el modelo a partir del código. Los primeros son de lectura y de decisión, y los últimos exigen manejar las herramientas.

    Herramientas

    La mayoría de los ejercicios se pueden resolver con lápiz y papel, aunque conviene comprobar el resultado con Dia. Los ejercicios 10, 11 y 12 son de manejo de herramientas y requieren Dia o IntelliJ IDEA instalados.

    1. Distinguir clases, atributos y operaciones

    Lee el siguiente enunciado y elabora tres listas: los conceptos que son clases, los que son atributos y los que son operaciones.

    Una empresa de alquiler de bicicletas dispone de un conjunto de bicicletas, cada una con un número de serie, un modelo y un estado de conservación. La empresa también registra a sus clientes, de los que guarda el NIF, el nombre y el teléfono. Cuando un cliente se lleva una bicicleta se anota la fecha de salida y la fecha de devolución. El sistema debe poder calcular el precio del alquiler a partir de las horas de uso.

    Clases (sustantivos que tienen datos y comportamiento propios):

    • Bicicleta
    • Cliente
    • Alquiler

    Atributos (datos que describen a otra cosa):

    • numeroSerie, modelo y estado de Bicicleta
    • NIF, nombre y telefono de Cliente
    • fechaSalida y fechaDevolucion de Alquiler

    Operaciones (verbos que expresan lo que el sistema hace):

    • calcularPrecio(), propia de Alquiler

    La prueba que distingue una clase de un atributo es si el concepto tiene vida propia. "Bicicleta" tiene datos y se relaciona con otros conceptos, así que es una clase. "Modelo" es un texto que describe una bicicleta, así que es un atributo. "Alquiler" es el caso interesante: no es ni una bicicleta ni un cliente, sino el vínculo entre los dos, y por eso se convierte en una clase con sus propias fechas.

    2. Trazar un diagrama de clases

    Dibuja el diagrama de clases que corresponde al siguiente enunciado, indicando qué se representa con cada símbolo.

    Una biblioteca presta libros a sus socios. De cada libro se guarda el ISBN, el título y el autor. De cada socio, el DNI, el nombre y el teléfono. Un socio puede tener prestados como máximo tres libros a la vez, y un libro solo puede estar en manos de un socio. Existen dos tipos de socio, infantil y adulto, y de los infantiles interesa además el nombre del tutor que firma su carné. Un socio puede pedir el préstamo de un libro, operación que devuelve si la operación se ha podido realizar o no.

    classDiagram
    class Libro {
        -isbn : String
        -titulo : String
        -autor : String
    }
    class Socio {
        -dni : String
        -nombre : String
        -telefono : String
        +prestar(l : Libro) boolean
    }
    class SocioInfantil {
        -tutor : String
    }
    Socio <|-- SocioInfantil
    Socio "1" --> "0..3" Libro : presta

    La correspondencia entre el enunciado y el dibujo es la siguiente:

    • Clases: Libro, Socio y SocioInfantil. Los atributos van precedidos del símbolo - porque, siguiendo el principio de encapsulación, los datos de un objeto solo los toca el propio objeto.
    • Operación: prestar() en Socio, con un parámetro de tipo Libro y valor de retorno booleano. El enunciado dice que devuelve si la operación se ha podido hacer o no, y esa información es un booleano.
    • Generalización: la flecha con punta triangular hueca sale de SocioInfantil y apunta a Socio, porque un socio infantil es un socio. Los atributos comunes (dni, nombre, telefono) se declaran una sola vez, en la clase madre.
    • Asociación con navegabilidad: la flecha apunta de Socio a Libro, porque el socio es quien conoce sus préstamos y el libro no necesita saber quién lo tiene. Si en algún momento hiciera falta el camino inverso, habría que añadirlo de forma consciente.
    • Multiplicidad: 1 en el extremo de Socio y 0..3 en el de Libro. Se lee "un socio tiene prestados de cero a tres libros", que es exactamente lo que dice el enunciado.

    3. Interpretar un diagrama de clases

    Observa el diagrama de la asociación Préstamo del apartado teórico, en el que Libro aparece con la multiplicidad 0..3 y Lector con la multiplicidad 0..1, y responde:

    1. ¿Cuántos lectores puede tener un libro concreto en un momento dado?
    2. ¿Cuántos libros puede tener un lector a la vez?
    3. ¿Puede existir un libro sin ningún lector?
    4. ¿Qué habría que cambiar para permitir que un libro pudiera estar prestado a la vez a varios lectores?

    La regla para leer multiplicidades es sencilla y conviene no equivocarla: cada valor se coloca en el extremo de la clase contraria a la que se está leyendo.

    1. Un libro puede tener como máximo un lector, porque el 0..1 está del lado del lector.
    2. Un lector puede tener a la vez entre cero y tres libros, porque el 0..3 está del lado del libro.
    3. Sí. El mínimo del intervalo es cero, lo que significa que el libro puede existir sin estar prestado.
    4. Bastaría con sustituir el 0..1 del extremo de Lector por 0..* o por 1..*, según si se admite que el libro esté sin prestar o no. Hay que modificar el extremo del lector, no el del libro, porque la multiplicidad describe cuántos objetos de la otra clase participan.

    4. La visibilidad

    Dada la siguiente clase Java, dibuja el rectángulo UML correspondiente con los símbolos de visibilidad en cada miembro.

    public class CuentaBancaria {

    private String titular;
    private double saldo;
    protected String sucursal;

    public CuentaBancaria(String titular, String sucursal) { ... }

    public double consultarSaldo() { ... }

    protected void aplicarIntereses(double tipo) { ... }

    private boolean validarImporte(double importe) { ... }
}
    Fila del rectángulo Contenido
    Nombre CuentaBancaria
    Atributos - titular : String, - saldo : double, # sucursal : String
    Operaciones + CuentaBancaria(titular : String, sucursal : String), + consultarSaldo() : double, # aplicarIntereses(tipo : double) : void, - validarImporte(importe : double) : boolean

    El reparto no es arbitrario y tiene una lectura práctica. titular y saldo son privados porque nadie de fuera debe poder escribir en ellos: el saldo solo cambia a través de operaciones controladas. sucursal es protegido porque las clases que hereden de CuentaBancaria sí necesitan consultarlo. Y validarImporte() es privado porque es un detalle interno de la clase: si mañana cambia la forma de validar un importe, ningún otro trozo del programa debería enterarse.

    6. Agregación o composición

    Decide si cada caso es una agregación o una composición y explica en qué te has basado:

    1. Un Equipo de fútbol y sus Jugador.
    2. Un Pedido y sus LíneaDePedido.
    3. Una Orquesta y sus Músico.
    4. Un Coche y su Motor.

    La pregunta que decide no es si la parte tiene sentido por sí sola, sino qué ocurre con la parte cuando desaparece el todo.

    1. Agregación. Si el equipo se disuelve, los jugadores siguen existiendo y pueden fichar por otro equipo.
    2. Composición. Una línea de pedido no significa nada fuera del pedido: no se puede comprar media línea de un pedido que ya no existe.
    3. Agregación. Los músicos existen con independencia de la orquesta y pueden tocar en otra.
    4. Composición. Un motor separado del coche deja de ser el motor de ese coche y pierde su función; el chasis se diseñó para ese motor concreto.

    Merece la pena fijarse en que los cuatro casos son relaciones todo-parte, y que la diferencia no está en el dibujo, sino en la semántica. De ahí que el error más habitual sea dibujar el rombo relleno por costumbre: equivocarse obliga después a programar la destrucción en cascada de objetos que debían sobrevivir, o a mantener con vida objetos que ya no tienen sentido.

    7. La clase asociativa

    Un centro educativo quiere registrar las notas de sus alumnos. De cada alumno guarda el expediente y el nombre; de cada módulo, el código y la denominación. Cada alumno cursa varios módulos, y en cada módulo obtiene una nota. ¿Dónde se coloca el atributo nota? Dibuja la solución.

    La nota no puede ir en Alumno, porque un alumno tiene tantas notas como módulos curse. Tampoco puede ir en Modulo, porque un módulo tiene tantas notas como alumnos matriculados. La nota pertenece al vínculo entre los dos, y ese es exactamente el caso que resuelve la clase asociativa.

    classDiagram
    class Alumno {
        -expediente : String
        -nombre : String
    }
    class Modulo {
        -codigo : String
        -denominacion : String
    }
    class Matricula {
        -nota : double
    }
    Alumno "1..*" -- "*" Modulo : cursa
    Matricula .. Alumno
    Matricula .. Modulo

    La clase Matricula se une a la línea de la asociación mediante una línea discontinua, y representa el mismo elemento conceptual que la asociación cursa: no es una cuarta clase añadida, sino la asociación misma convertida en clase para poder llevar sus propios datos. Si en lugar de esto se hubiera puesto el atributo nota dentro de Alumno, el modelo obligaría a guardar una lista de notas en paralelo a la lista de módulos, y mantener las dos sincronizadas pasaría a ser responsabilidad de quien programe.

    8. La interfaz y su realización

    Se quiere que el sistema pueda trabajar con distintos medios de pago (tarjeta, transferencia y efectivo) sin que el código que cobra tenga que saber cuál está usando. Define la interfaz y dibuja la relación de realización.

    interface MedioPago {
    boolean cobrar(double importe);
    String getDescripcion();
}

    Cada medio concreto implementa el contrato:

    public class Tarjeta implements MedioPago {
    @Override
    public boolean cobrar(double importe) { ... }

    @Override
    public String getDescripcion() { return "Tarjeta"; }
}

    classDiagram
    class MedioPago {
        <<interface>>
        +cobrar(importe : double) boolean
        +getDescripcion() String
    }
    class Tarjeta
    class Transferencia
    class Efectivo
    MedioPago <|.. Tarjeta
    MedioPago <|.. Transferencia
    MedioPago <|.. Efectivo

    La línea discontinua con el triángulo hueco es la realización, y apunta siempre a la interfaz. La ventaja se aprecia en el código que cobra: puede escribir MedioPago medio = new Tarjeta(); medio.cobrar(120.5); sin saber qué implementación concreta tiene delante. Si mañana aparece un cuarto medio de pago, basta con crear la clase; el código de cobro no se toca. Es el mismo principio del puerto USB: mientras se respete la forma del conector, el dispositivo que se enchufe es indiferente.

    9. Corregir un diagrama

    Un compañero ha dibujado el diagrama de clases de una tienda online y ha cometido tres errores. Localízalos y explica cómo se corrigen.

    Cliente tiene como atributos id, nombre y una lista de Pedido. Pedido tiene fecha y total, y hereda de Cliente porque un pedido pertenece a un cliente. Producto tiene referencia, nombre y precio. La relación entre Pedido y Producto está dibujada con un rombo relleno del lado del pedido, porque un pedido está compuesto por productos.

    Error 1: herencia donde hay asociación. Que un pedido pertenezca a un cliente no convierte al pedido en un tipo de cliente. La herencia expresa identidad ("un pedido es un cliente", que es falso) y además crea el acoplamiento más fuerte que existe: cualquier cambio en Cliente arrastraría a todos sus pedidos. Lo correcto es una asociación entre Pedido y Cliente, con la multiplicidad correspondiente.

    Error 2: una lista como atributo. Guardar "una lista de Pedido" dentro de Cliente es mezclar el modelo con su implementación. En el diagrama de clases se dibuja la asociación y es la multiplicidad la que informa de que son varios; la lista concreta es una decisión del código, no del modelo.

    Error 3: composición mal elegida. La composición implica que las líneas del pedido desaparecen con él, y eso es cierto, pero el rombo relleno está puesto del lado del pedido en relación con la clase Producto, y eso significaría que el catálogo de productos se destruye cuando se borra un pedido. Lo que se destruye con el pedido es la línea de pedido, no el producto. La solución correcta es crear una clase LineaPedido en composición con Pedido y asociada a Producto, que sigue existiendo con independencia de las ventas.

    10. Dibujar el modelo en Dia y generar el código

    Toma el diagrama de clases del ejercicio 2, constrúyelo en Dia y genera el código Java correspondiente. Después localiza en el código generado qué partes están completas y qué partes hay que escribir a mano.

    Los pasos son los siguientes:

    1. Crear un documento nuevo y seleccionar la hoja de formas UML en la caja de herramientas.
    2. Arrastrar tres formas Class al lienzo y darles los nombres Libro, Socio y SocioInfantil.
    3. Abrir las propiedades de cada clase y añadir sus atributos con el tipo y la visibilidad que aparecen en el diagrama.
    4. Trazar una Generalization desde SocioInfantil hasta Socio, y una Association entre Socio y Libro cuyos extremos se configuran en las propiedades de la relación: multiplicidad 1 en el extremo del socio y 0..3 en el del libro, con la navegabilidad marcada hacia el libro.

    5. Guardar el documento como biblioteca.dia y generar el código con dia2code:

      sudo apt install dia2code
dia2code -t java biblioteca.dia

    Lo que la herramienta escribe sola es la estructura: las declaraciones de clase, la cláusula extends de SocioInfantil, los atributos con sus tipos y su visibilidad, y los métodos de acceso que se hayan declarado en el modelo. Lo que queda pendiente es la lógica: el cuerpo de prestar() aparece vacío, porque ninguna herramienta puede deducir de un dibujo qué reglas debe comprobar ese método. Esa frontera entre lo que se genera y lo que se programa a mano es la que conviene entender: el modelo ahorra el trabajo mecánico, no el trabajo de pensar.

    11. Ingeniería inversa y comparación de modelos

    Abre en IntelliJ el código Java que has generado en el ejercicio anterior y obtén su diagrama de clases. A continuación compara ese diagrama con el que dibujaste a mano en Dia y responde: ¿son idénticos?, ¿qué elementos aparecen en uno y no en el otro?, ¿por qué el diagrama generado por el IDE no puede contener nada que no esté en el código?

    El procedimiento con IntelliJ es el siguiente:

    1. Comprobar que el módulo Diagrams está activo en Ctrl+Alt+S → Plugins → Installed.
    2. Abrir el proyecto Java y, en el tool window Project, pulsar con el botón derecho sobre el paquete y escoger Diagrams | Show Diagram (Ctrl+Alt+Shift+U), seleccionando después Java Class Diagram.

    Los dos diagramas no son idénticos, y las diferencias son el contenido real del ejercicio. El diagrama dibujado en Dia puede contener elementos que el código todavía no refleja, porque representa una intención de diseño: si en el modelo se dibujó prestar() pero el método se dejó vacío, el diagrama de Dia sigue mostrándolo mientras que el de IntelliJ mostrará el método tal y como está escrito en el código. Al contrario, el diagrama del IDE puede mostrar cosas que en el modelo dibujado no estaban, como los constructores que la herramienta generó por su cuenta o los métodos de acceso que se añadieron después de dibujar.

    La razón de fondo es que el diagrama de IntelliJ no se guarda en ningún archivo, sino que se reconstruye cada vez leyendo el proyecto. Por eso no puede contener nada que no esté en el código: no tiene memoria propia. Un diagrama dibujado a mano sí tiene memoria, y esa memoria es exactamente lo que el round-trip pretende mantener sincronizado con el código, con el riesgo de que se desincronice.

    12. Crear estructura de código desde el diagrama

    Abre el proyecto Java de la biblioteca en IntelliJ, genera el diagrama del paquete y añade desde el propio diagrama un campo nuevo a Libro (por ejemplo editorial) y una clase nueva Bibliotecario. Comprueba qué ocurre en el código fuente y explica qué acaba de suceder.

    El procedimiento es el siguiente:

    1. Generar el diagrama del paquete con Diagrams | Show Diagram (Ctrl+Alt+Shift+U) y elegir Java Class Diagram.
    2. Con el botón derecho sobre el lienzo, escoger Content | New y, en el submenú, el elemento que se quiera crear: un campo, un método o una clase. El IDE abre el diálogo correspondiente, pide los datos necesarios y añade el elemento a la vez al diagrama y al árbol del proyecto.
    3. Con el botón Edge Creation mode de la barra del diagrama se puede trazar una relación entre dos clases; al hacerlo, IntelliJ modifica el código fuente en consecuencia: si la relación es una asociación, crea el atributo correspondiente; si es una herencia, añade el extends.

    Lo que acaba de suceder es que se ha recorrido el camino del diseño al código dentro del propio IDE: el diagrama ha dejado de ser una vista de solo lectura y ha pasado a ser una herramienta de edición del programa. Es la forma de cubrir la generación de código a partir de un diagrama sin salir del entorno, con una diferencia importante respecto a un generador de código al uso: aquí no se genera un proyecto entero de golpe, sino que cada elemento se escribe en el código en el momento en que se añade al dibujo. Por eso este mecanismo no sustituye al diseño previo, pero sí permite mantener el modelo y el programa pegados el uno al otro.

    13. Decidir la navegabilidad

    En el modelo de la biblioteca, la asociación entre Socio y Libro está dibujada de tal forma que solo se puede recorrer del socio al libro. Razona si esa decisión es correcta y qué consecuencias tiene en el código.

    La decisión es correcta y es la que corresponde a la mayoría de los casos reales. El socio necesita conocer los libros que tiene prestados para poder devolverlos, y esa necesidad existe en el momento de la devolución: se busca al socio y, desde él, el libro. En cambio, el flujo contrario no lo pide nadie: al devolver un libro por su ISBN no hace falta preguntar a quién se lo llevó, porque el sistema ya partió del socio.

    Navegar en un solo sentido tiene dos consecuencias en el código. La primera es de tipo práctico: solo la clase Socio lleva un atributo con la colección de libros, de modo que no hay dos listas que mantener sincronizadas. La segunda es de tipo conceptual: la clase Libro queda más simple y no arrastra responsabilidades que no le pertenecen.

    Lo que no conviene hacer es dejar la asociación sin flechas "por si acaso". Una asociación bidireccional obliga a las dos clases a guardar una referencia a la otra, y a partir de ahí cualquier operación que añada o borre un préstamo tiene que actualizar los dos lados; si alguien olvida uno, el modelo queda incoherente y el fallo aparece mucho después y en otro sitio. Si en algún momento hiciera falta recorrer el camino contrario, casi siempre sale más barato resolverlo con una consulta que duplicando la estructura.

    14. Dibujar un diagrama de objetos

    A partir del diagrama de clases del ejercicio 2, dibuja el diagrama de objetos que representa la situación siguiente: la socia Marta Ferri (DNI 33445566) tiene prestados dos libros, El Quijote y La Regenta, y el socio Pau Sanchis (DNI 11223344), que es infantil y tiene como tutor a Ana Ribes, no tiene ningún libro prestado.

    El diagrama de objetos contiene solo instancias y los enlaces entre ellas, y cada instancia se escribe con la notación nombre : Clase:

    Objeto Clase Valores de los atributos
    marta : Socio Socio dni = "33445566", nombre = "Marta Ferri", telefono = "..."
    pau : SocioInfantil SocioInfantil dni = "11223344", nombre = "Pau Sanchis", tutor = "Ana Ribes"
    q : Libro Libro isbn = "978-84-376-0494-7", titulo = "El Quijote", autor = "Cervantes"
    r : Libro Libro isbn = "978-84-7039-123-4", titulo = "La Regenta", autor = "Clarín"

    Los enlaces unen marta con q y marta con r, y no hay ningún enlace que salga de pau. La comparación con el diagrama de clases es lo que da valor al ejercicio: lo que allí era un 1 y un 0..3 se ha convertido aquí en una instancia concreta con dos enlaces, y cualquier duda sobre si el modelo admite o no esa situación se resuelve comprobando que los enlaces respetan las multiplicidades. Con Pau se comprueba además que el mínimo del intervalo es cero: un socio sin préstamos es una situación válida, no un error del modelo.

    15. Distinguir clases, atributos y operaciones (2)

    Lee el enunciado y separa los conceptos en clases, atributos y operaciones.

    Un aeropuerto gestiona vuelos. De cada vuelo se guarda el código, la hora de salida y la hora de llegada. Los vuelos salen de una puerta de embarque y llegan a otra. De cada pasajero se guarda el pasaporte, el nombre y la nacionalidad, y cada pasajero puede reservar varios vuelos, con una fecha de reserva y un asiento. El sistema debe poder calcular el tiempo de vuelo a partir de las horas.

    Clases: Vuelo, Pasajero, Puerta y Reserva.

    Atributos:

    • codigo, horaSalida, horaLlegada de Vuelo
    • pasaporte, nombre, nacionalidad de Pasajero
    • numero de Puerta
    • fechaReserva, asiento de Reserva

    Operaciones:

    • calcularTiempoVuelo() de Vuelo

    Reserva vuelve a ser el caso interesante: ni el vuelo ni el pasajero son suyos, sino el vínculo entre ambos, así que fechaReserva y asiento no pertenecen a ninguna de las dos clases. Puerta es una clase y no un simple texto porque tiene identidad propia: un vuelo sale de una puerta concreta, y esa puerta existe con independencia de qué vuelos la usen.

    16. Interpretar multiplicidades y navegabilidad

    Observa el diagrama y responde:

    classDiagram
    class Profesor {
        -id : String
        -nombre : String
    }
    class Asignatura {
        -codigo : String
        -nombre : String
    }
    Profesor "1" --> "1..*" Asignatura : imparte
    1. ¿Cuántas asignaturas puede impartir un profesor?
    2. ¿Cuántos profesores puede tener una asignatura?
    3. ¿Puede existir un profesor sin asignaturas?
    4. ¿Qué cambia si la flecha se dibujara también en el sentido contrario?
    1. Entre una y varias (1..*), porque el valor está en el extremo de Asignatura.
    2. Uno solo, porque el 1 está en el extremo de Profesor.
    3. No: el mínimo del intervalo es 1, así que todo profesor imparte al menos una asignatura.
    4. Que ambas clases tendrían que guardar una referencia a la otra. Con la navegabilidad actual solo Profesor conoce sus asignaturas; si se hiciera bidireccional, cada alta o baja habría que actualizarla en los dos lados, y bastaría un olvido para dejar el modelo incoherente.

    La lectura correcta coloca siempre cada multiplicidad en el extremo de la clase contraria a la que se está describiendo. Confundir de qué lado va cada número es el error más frecuente al empezar.

    17. Herencia y clase abstracta

    Diseña el modelo de las figuras geométricas: un Circulo y un Rectangulo comparten las operaciones area() y perimetro(), pero no tiene sentido crear una figura genérica sin forma. Dibuja el diagrama.

    classDiagram
    class Figura {
        <<abstract>>
        #nombre : String
        +area() double
        +perimetro() double
    }
    class Circulo {
        -radio : double
        +area() double
        +perimetro() double
    }
    class Rectangulo {
        -base : double
        -altura : double
        +area() double
        +perimetro() double
    }
    Figura <|-- Circulo
    Figura <|-- Rectangulo

    Figura se marca como abstracta (nombre en cursiva o el estereotipo <<abstract>>), y eso significa que no se instancia: no existe un objeto "figura sin forma". Las operaciones area() y perimetro() se declaran en la madre porque todas las hijas las ofrecen, pero no se implementan allí, porque cada figura calcula a su manera. nombre es protected (#) porque las hijas lo usan directamente y nadie de fuera debe tocarlo.

    El valor del ejercicio está en la decisión de la parte alta: si Figura fuera concreta, el modelo estaría afirmando que puede existir una figura genérica, y eso no es cierto.

    18. Interfaz o clase abstracta

    Indica si cada caso pide una interfaz o una clase abstracta y por qué:

    1. MedioPago, del que cuelgan Tarjeta, Transferencia y Efectivo, que solo comparten el contrato cobrar().
    2. Empleado, del que cuelgan Fijo y Temporal, que comparten el atributo nombre y el método antiguedad() ya implementado.
    3. Reproductor, del que cuelgan ReproductorAudio y ReproductorVideo, que comparten código común y además cumplen el contrato Playable.
    1. Interfaz. Los tres medios de pago no comparten ningún dato ni código: solo se comprometen a ofrecer cobrar(). Eso es un contrato, no una herencia de comportamiento.
    2. Clase abstracta. Hay estado y lógica comunes (nombre, antiguedad()) que conviene escribir una sola vez y heredar.
    3. Las dos. Reproductor es una clase abstracta porque aporta código común, y además implementa Playable porque cumple un contrato externo. Es habitual que una clase abstracta implemente una interfaz.

    La regla práctica es clara: si solo hay un contrato, interfaz; si hay código o datos que reutilizar, clase abstracta.

    19. La clase asociativa (con fechas)

    En un hotel, un Cliente reserva Habitacion en distintas fechas. De cada reserva interesa la fecha de entrada, la de salida y el precio acordado. ¿Dónde van esos tres datos? Dibuja la solución.

    classDiagram
    class Cliente {
        -dni : String
        -nombre : String
    }
    class Habitacion {
        -numero : int
        -planta : int
    }
    class Reserva {
        -fechaEntrada : Date
        -fechaSalida : Date
        -precio : double
    }
    Cliente "1" -- "*" Habitacion : reserva
    Reserva .. Cliente
    Reserva .. Habitacion

    Ni Cliente ni Habitacion pueden guardar esos datos: un cliente reserva muchas veces y una habitación se reserva muchas veces también. Las tres cosas describen el vínculo, y ese vínculo se convierte en la clase asociativa Reserva, unida a la asociación por una línea discontinua. El precio es, además, el dato más típicamente asociativo: la misma habitación cuesta distinto según la temporada, así que no puede vivir dentro de Habitacion.

    21. De código Java a diagrama (ingeniería inversa)

    Dado el siguiente código, dibuja el diagrama de clases correspondiente.

    public abstract class Vehiculo {
    protected String matricula;
    public abstract double consumo();
}

public class Coche extends Vehiculo {
    private int puertas;
    public double consumo() { ... }
}

public class Moto extends Vehiculo {
    private int cilindrada;
    public double consumo() { ... }
}

public interface Electrico {
    void cargar();
}

    classDiagram
    class Vehiculo {
        <<abstract>>
        #matricula : String
        +consumo() double
    }
    class Coche {
        -puertas : int
        +consumo() double
    }
    class Moto {
        -cilindrada : int
        +consumo() double
    }
    class Electrico {
        <<interface>>
        +cargar() void
    }
    Vehiculo <|-- Coche
    Vehiculo <|-- Moto

    Las claves están en tres detalles del código. abstract class produce una clase abstracta, que se marca con <<abstract>>. El modificador protected de matricula se dibuja con #, y el private con -. Y la palabra interface se traduce a una clase con el estereotipo <<interface>>, sin casilla de atributos porque no tiene estado. Si alguna clase implementara Electrico, la flecha sería de realización (línea discontinua con punta triangular hueca), no de generalización.

    Este ejercicio es el inverso del 10: en lugar de pasar del dibujo al código, se reconstruye el modelo leyendo el programa. Es el mecanismo que usan las herramientas de ingeniería inversa (el diagrama de IntelliJ del ejercicio 11), y hacerlo a mano una vez ayuda a entender qué se puede y qué no se puede recuperar automáticamente.

    22. Elegir la multiplicidad

    Asigna la multiplicidad de cada extremo y explica qué significa en cada caso:

    1. Factura y LineaFactura: una factura tiene una o varias líneas.
    2. Pais y Capital: un país tiene exactamente una capital y una capital pertenece a un solo país.
    3. Alumno y Asignatura: un alumno cursa varias asignaturas, y una asignatura tiene varios alumnos.
    4. Persona y Direccion: una persona puede tener una dirección, y una dirección puede no estar asociada a nadie.
    1. Factura "1" -- "1..*" LineaFactura
    2. Pais "1" -- "1" Capital
    3. Alumno "*" -- "*" Asignatura
    4. Persona "0..1" -- "0..1" Direccion

    Cada intervalo responde a dos preguntas: el máximo dice cuántos puede haber y el mínimo si es obligatorio. El caso 3 es el que más se equivoca: cuando los dos extremos son *, la asociación es muchos a muchos y la base de datos necesitará una tabla intermedia, algo que conviene anticipar en el modelo. El caso 4 recuerda que el mínimo puede ser cero: una dirección sin persona es un valor válido, no un error.
