    Trabajo básico con Git

    Uno de los conceptos que más cuesta entender al empezar con Git, y que a la vez resulta fundamental para dominarlo, es su modelo de trabajo. A diferencia de lo que podría pensarse, cuando modificamos un archivo, Git no guarda el cambio de forma inmediata. Entre el momento en que editamos un fichero y el momento en que ese cambio queda registrado en el historial hay un recorrido, y Git divide ese recorrido en tres áreas o "lugares" bien diferenciados. Entender dónde está el código en cada momento es la clave para no perderse.

    1. El directorio de trabajo (working directory): es la carpeta del proyecto tal y como la vemos en el explorador de archivos o en el editor de código. Aquí es donde editamos, creamos y borramos archivos. Es, simplemente, nuestro trabajo de cada día, la superficie sobre la que escribimos.

    2. La zona de preparación (staging area, también llamada índice): es una zona intermedia, una especie de "bandeja de salida", donde indicamos a Git qué cambios queremos incluir en la próxima "foto". No todos los cambios tienen por qué incluirse: podemos haber modificado diez archivos y decidir que, de momento, solo nos interesa guardar los cambios de tres de ellos. Aquí es donde se decide qué entra en el próximo commit y qué se queda fuera.

    3. El repositorio local (.git): es la base de datos de Git, almacenada en la carpeta oculta .git que se crea dentro del proyecto. Aquí es donde Git guarda el historial completo: todos los commits con sus instantáneas, las ramas, las etiquetas, la configuración del repositorio y mucho más. Es el archivo definitivo, el lugar donde los cambios quedan a salvo.

    flowchart LR
    A["Directorio de trabajo<br/>(working directory)"] -->|"git add"| B["Zona de preparación<br/>(staging area)"]
    B -->|"git commit"| C["Repositorio local<br/>(.git)"]

    El flujo de trabajo es, por tanto, siempre el mismo y se repite en bucle a lo largo de toda la vida del proyecto:

    1. Modificamos los archivos en el directorio de trabajo. Es la parte cotidiana: escribir código, corregir errores, crear archivos nuevos.
    2. Preparamos los cambios con git add, que los traslada a la zona de preparación. Aquí seleccionamos qué queremos guardar.
    3. Confirmamos los cambios con git commit, que los guarda definitivamente en el repositorio local.

    ¿Por qué existe el paso intermedio de Staging?

    Puede parecer un engorro tener que pasar por un paso intermedio. ¿Por qué no guardar directamente con un solo comando, como hace cualquier procesador de textos con su botón de guardar? La respuesta es que esa separación, lejos de ser una complicación gratuita, es lo que da a Git un control muy fino sobre qué se guarda y cómo se cuenta la historia del proyecto.

    Imaginemos una situación muy habitual. Estamos trabajando en dos cosas a la vez: hemos corregido un error en una función y, de paso, hemos empezado a escribir una nueva funcionalidad a medias, aún sin terminar y sin probar. Si guardáramos todo junto con un solo comando, el historial quedaría con un commit que mezcla una corrección terminada con un trabajo a medias, y eso es un problema por varios motivos: si más adelante hay que revertir la corrección del error, nos llevaremos por delante también la funcionalidad incompleta; y si alguien revisa el historial, no entenderá qué se hizo realmente en ese commit.

    Con la zona de preparación, en cambio, podemos separar las dos cosas. Preparamos y confirmamos únicamente la corrección del error, dejando la funcionalidad sin terminar fuera del commit (permanece como "modificada" en el directorio de trabajo). De esta forma, cada commit refleja un cambio coherente y autónomo, y el historial se convierte en una narración limpia de la evolución del proyecto. La zona de preparación es, en definitiva, el mecanismo que permite contar la historia del código en unidades con sentido, en lugar de volcar bloques de cambios revueltos.

    Este control selectivo tiene otras aplicaciones prácticas: permite confirmar solo una parte de las líneas modificadas de un mismo archivo, preparar varios cambios distintos y confirmarlos por separado, o revisar con calma lo que se va a guardar antes de hacerlo definitivo. Es una diferencia sutil pero importante respecto a otras herramientas, y es una de las razones por las que Git se siente más potente una vez que se domina.

    Los estados de un archivo

    Como consecuencia de este modelo de tres áreas, cada archivo de un repositorio Git se encuentra siempre en uno de estos cuatro estados. Saber reconocerlos es lo que permite interpretar correctamente lo que Git nos dice en cada momento:

    • Sin seguimiento (untracked): el archivo existe en el directorio de trabajo, pero Git todavía no lo conoce, no forma parte del proyecto versionado. Suele ser el estado de todo archivo recién creado, hasta que se añade por primera vez.
    • Sin cambios (unmodified): el archivo está controlado por Git y no ha sufrido variaciones desde el último commit. Coincide exactamente con la versión guardada en el repositorio.
    • Modificado (modified): el archivo ha cambiado respecto al último commit, pero esos cambios todavía no se han añadido a la zona de preparación. Están en el directorio de trabajo, a la espera de que decidamos qué hacer con ellos.
    • Preparado (staged): los cambios se han añadido con git add y están listos para ser incluidos en el próximo commit. Es el estado justo antes de guardar.

    Estos estados no son compartimentos estancos: un archivo transita de uno a otro según las operaciones que hacemos. Un archivo recién creado empieza como untracked; al añadirlo con git add pasa a staged; al confirmarlo con git commit pasa a unmodified; y en cuanto lo volvemos a editar, pasa a modified. Conocer este ciclo es clave para interpretar correctamente la salida de comandos como git status, que veremos enseguida, y para no alarmarse cuando Git nos dice que un archivo está en un estado que no esperábamos.

    Crear un repositorio

    Existen dos formas de obtener un repositorio Git: crear uno nuevo desde cero o clonar uno ya existente. Para crear un repositorio nuevo a partir de una carpeta de nuestro proyecto, nos situamos en ella y ejecutamos:

    git init

    Este comando crea la carpeta oculta .git dentro del directorio actual, y con ella toda la infraestructura interna que Git necesita para llevar el control de versiones. A partir de ese momento, la carpeta es un repositorio Git y ya podemos empezar a versionar su contenido. Conviene insistir en que todo el historial y toda la información de Git vive dentro de .git: si se borra esa carpeta, se pierde el repositorio entero (aunque no los archivos del directorio de trabajo, que seguirían ahí como simples archivos sueltos, sin historial). Es un detalle que sorprende a mucha gente: el proyecto visible y el historial de Git son cosas distintas, y .git es el cofre donde se guarda lo segundo.

    Si el proyecto todavía no existe, el orden habitual es crear primero la carpeta, entrar en ella y ejecutar git init:

    mkdir mi-proyecto
cd mi-proyecto
git init

    Realizar el primer commit

    Una vez inicializado el repositorio, ya podemos guardar la primera "foto" del proyecto. Supongamos que acabamos de crear un archivo, por ejemplo HolaMundo.java. Si ejecutamos git status, Git nos dirá que ese archivo está sin seguimiento:

    Archivos sin seguimiento:
  (usa "git add <archivo>..." para incluirlos en lo que será confirmado)
    HolaMundo.java

    Que esté sin seguimiento significa que Git lo ve, pero no lo ha incorporado todavía al control de versiones. El primer paso es añadirlo a la zona de preparación. Para añadir un archivo concreto:

    git add HolaMundo.java

    Para añadir todos los archivos del directorio a la vez (algo muy habitual cuando se ha modificado mucho código):

    git add .

    El punto . es una referencia al directorio actual, por lo que git add . prepara todos los archivos del proyecto de una sola vez. Es cómodo, pero conviene usarlo con un poco de cuidado: si hay archivos que no deberían versionarse (temporales, credenciales, configuraciones locales), se colarán igualmente. Por eso es buena costumbre revisar después con git status que se está preparando exactamente lo que se quería.

    Una vez preparados los cambios, los confirmamos con un commit:

    git commit -m "Crear la clase HolaMundo"

    El parámetro -m permite indicar el mensaje del commit directamente en la línea de comandos. Si se omite, Git abrirá el editor de texto configurado para que escribamos el mensaje allí, lo cual es útil para mensajes largos pero engorroso para los cortos.

    El mensaje del commit es más importante de lo que parece, porque es la voz del historial. Un buen mensaje debe describir qué se ha hecho y por qué, en imperativo y de forma breve pero informativa. Conviene pensar que, dentro de unos meses, tú o un compañero leeréis el historial preguntándoos "¿qué se hizo aquí?". Mensajes como "cambios varios" o "arreglado" no aportan nada y obligan a abrir el commit para entenderlo. En cambio, "Corregir el cálculo del IVA en la factura" o "Añadir validación del DNI" se explican solos. Existen convenciones formales para redactar estos mensajes, pero lo fundamental, sobre todo al principio, es ser claro y concreto.

    Consultar el estado del repositorio

    El comando git status es, probablemente, el que más se usa de todo Git, y conviene ejecutarlo con frecuencia. Muestra información valiosísima: en qué rama estamos, qué archivos están modificados, cuáles están preparados y cuáles no tienen seguimiento. Es como la pantalla de instrumentos del proyecto.

    git status

    La salida de git status está pensada para ser autodescriptiva, e incluso incluye sugerencias de los comandos que podemos ejecutar a continuación. Acostumbrarse a consultarlo antes y después de cada operación evita muchísimos errores y sustos, porque permite ver el estado real antes de tomar decisiones. Es el equivalente a mirar antes de cruzar.

    Consultar el historial

    Para ver los commits que se han realizado a lo largo de la vida del proyecto, se usa git log:

    git log

    La salida muestra, por cada commit, un identificador único (un hash como 9fceb02), el autor, la fecha y el mensaje. El orden es del más reciente al más antiguo, de manera que lo último que se hizo aparece arriba. Ese hash es importante, porque es la referencia que se usa para nombrar un commit concreto cuando queremos volver a él.

    A medida que el proyecto crece, esa salida se vuelve demasiado larga y difícil de leer. Por eso resultan muy útiles las versiones compactas:

    git log --oneline

    muestra cada commit en una sola línea, y

    git log --oneline --graph

    añade además un pequeño diagrama de las ramas, lo que permite visualizar de un vistazo cómo se ha ramificado y fusionado el proyecto. Este último es especialmente valioso cuando se empieza a trabajar con ramas, porque convierte un historial abstracto en algo que se puede "ver".

    Ver las diferencias

    Cuando queremos ver exactamente qué líneas han cambiado en un archivo, usamos git diff. Este comando es una herramienta imprescindible para revisar el propio trabajo antes de confirmarlo, y también para entender los cambios que otros han hecho.

    Para ver los cambios que todavía no se han preparado (es decir, la diferencia entre el directorio de trabajo y la zona de preparación):

    git diff

    Para ver los cambios que sí están preparados y se incluirán en el próximo commit (la diferencia entre la zona de preparación y el último commit):

    git diff --staged

    La distinción entre estos dos comandos refleja de nuevo el modelo de las tres áreas: uno mira lo que aún está "suelto" en el directorio de trabajo, y el otro mira lo que ya está listo para guardarse.

    Trabajar con ramas

    Las ramas (branches) son una de las características más potentes de Git y, sin duda, una de las más utilizadas. Para entenderlas de verdad, hay que empezar por un detalle conceptual que sorprende: en Git, una rama no es una copia de los archivos, sino un simple puntero a un commit concreto. Es decir, una rama es apenas un nombre que apunta a uno de los puntos del historial, y se va moviendo hacia adelante a medida que se hacen nuevos commits sobre ella.

    Ese detalle lo cambia todo. Como una rama es solo un puntero, crear una rama es instantáneo y no ocupa espacio: no se duplican archivos, solo se crea una nueva etiqueta que señala a un punto del historial. La rama principal del repositorio suele llamarse main, y a partir de ella se pueden crear tantas ramas secundarias como se quiera.

    La utilidad de las ramas está en el aislamiento. La idea es la siguiente: en lugar de trabajar directamente sobre la rama principal, cuando vamos a desarrollar una nueva funcionalidad o a corregir un error, creamos una rama nueva. Mientras trabajamos en esa rama, la rama principal permanece intacta y estable, sin verse afectada por lo que estamos haciendo. Es como trabajar en una copia paralela del proyecto: podemos romper, experimentar y equivocarnos sin poner en riesgo la versión buena. Cuando la funcionalidad está terminada y probada, fusionamos la rama con la principal, y solo entonces el trabajo se incorpora al código estable.

    Las ramas también permiten que varias personas trabajen en paralelo sin pisarse: cada una trabaja en su propia rama y, al final, los resultados se fusionan. Esta forma de trabajar es la base de prácticamente todos los equipos de desarrollo modernos, y es lo que permite que una persona arregle un error urgente mientras otra sigue desarrollando una funcionalidad sin que ninguna interfiera con la otra.

    Los comandos básicos para manejar ramas son los siguientes:

    • Para listar las ramas existentes (la rama actual se marca con un asterisco):

      git branch

    • Para crear una nueva rama:

      git branch nombre-de-la-rama

    • Para cambiar a una rama:

      git switch nombre-de-la-rama

    • Para crear una rama y cambiar a ella de una sola vez:

      git switch -c nombre-de-la-rama

    • Para fusionar una rama con la rama en la que nos encontramos:

      git merge nombre-de-la-rama

    Nota sobre checkout

    En muchos tutoriales y libros todavía se verá el comando git checkout para cambiar de rama, ya que históricamente era la forma de hacerlo. Las versiones modernas de Git añadieron git switch, que es más claro y se recomienda para esta tarea. git checkout sigue existiendo, pero con otros usos (como descartar cambios), que veremos más adelante.

    El siguiente diagrama ilustra un flujo de trabajo típico con ramas: se parte de la rama main, se crea una rama feature para desarrollar una funcionalidad y, cuando está terminada, se fusiona de nuevo con main:

    gitGraph
    commit id: "Inicial"
    commit id: "c1"
    branch feature
    checkout feature
    commit id: "c2"
    commit id: "c3"
    checkout main
    commit id: "c4"
    merge feature

    Fusionar ramas y resolver conflictos

    Fusionar (hacer merge) es la operación de integrar en la rama actual los cambios que se hicieron en otra rama. En la mayoría de los casos, Git lo hace solo, de forma automática: si los cambios de una rama y otra afectan a partes distintas del código, no hay nada que decidir y la fusión se completa sin intervención. El resultado es un commit de fusión que reúne las dos líneas de trabajo.

    El problema surge cuando las dos ramas han tocado exactamente la misma parte de un archivo. Ahí Git no puede decidir por sí solo qué versión es la buena, y se produce un conflicto. La resolución de un conflicto es una de las habilidades más valiosas que se aprenden con Git, y merece la pena verla paso a paso:

    1. Se lanza la fusión con git merge y Git informa de que no ha podido completarla porque hay un conflicto en uno o varios archivos.
    2. Si abrimos el archivo en conflicto, encontramos unas marcas que Git ha insertado para mostrar las dos versiones enfrentadas: la parte de arriba corresponde a la versión de la rama actual y la de abajo a la versión de la rama que se está fusionando.
    3. El desarrollador decide manualmente qué hacer: quedarse con una de las dos versiones, con la otra, o combinar ambas para que el resultado tenga sentido. Para ello, borra las marcas y deja el archivo en su forma definitiva.
    4. Una vez resuelto el archivo, se prepara con git add y se cierra la fusión con git commit. Git crea entonces el commit de fusión y el conflicto queda resuelto.

    Conviene no temer a los conflictos: son normales, aparecen solo cuando dos personas han tocado lo mismo, y su resolución es una tarea manual, sí, pero acotada y puntual. Es mucho mejor esto que los bloqueos que obligaban a turnarse: aquí cada uno trabaja a su aire y el conflicto, cuando surge, se resuelve una sola vez.

    Deshacer cambios

    Todos cometemos errores, y una de las grandes ventajas de Git es que permite deshacerlos de distintas formas según la situación. La dificultad no está en recordar los comandos, sino en entender qué hace cada uno exactamente y en qué caso conviene aplicar cada técnica. A continuación se recorren las más habituales, prestando atención a qué le ocurre a los archivos que están en disco.

    Descartar los cambios de un archivo

    Si hemos modificado un archivo y queremos descartar esos cambios para volver a la última versión confirmada, usamos:

    git checkout -- nombre-del-archivo

    Este comando sobreescribe el archivo del directorio de trabajo con la versión que está guardada en el repositorio. Dicho de otro modo, los cambios que teníamos desaparecen del disco y el archivo vuelve a estar como en el último commit. Es útil cuando nos damos cuenta de que la dirección que habíamos tomado no era la correcta, pero conviene ser consciente de que esos cambios se pierden para siempre, porque nunca llegaron a guardarse en el historial. No hay forma de recuperarlos.

    Quitar un archivo de la zona de preparación

    Si hemos ejecutado git add por error y queremos que un archivo deje de estar preparado, usamos:

    git reset nombre-del-archivo

    Este comando no toca el contenido del archivo: simplemente lo saca de la zona de preparación y lo devuelve al directorio de trabajo, donde vuelve a quedar en estado "modificado". Los cambios siguen ahí, intactos; lo único que se deshace es la decisión de incluirlos en el próximo commit. Es la forma de "arrepentirse" de un git add sin perder nada.

    Deshacer el último commit

    Si ya hemos hecho un commit y queremos deshacerlo, hay varias opciones según lo que queramos conservar. La herramienta base es git reset, que mueve el puntero del historial hacia atrás, pero que tiene tres variantes que afectan de forma distinta a lo que está en disco y en la zona de preparación:

    • git reset --soft HEAD~1: deshace el commit, pero conserva los cambios en la zona de preparación. Los archivos no se tocan en disco y siguen listos para volver a confirmarse. Es ideal cuando el commit estaba bien pero el mensaje era incorrecto, o cuando se hizo antes de tiempo y se quiere rehacer.
    • git reset --mixed HEAD~1 (la variante por defecto): deshace el commit y deja los cambios en el directorio de trabajo, sacándolos de la zona de preparación. Los archivos siguen modificados en disco, pero habría que volver a hacer git add para confirmarlos. Útil para reordenar o reagrupar los cambios.
    • git reset --hard HEAD~1: deshace el commit y elimina por completo los cambios, tanto de la zona de preparación como del disco. Los archivos vuelven al estado del commit anterior y las modificaciones se pierden irremediablemente.

    La notación HEAD~1 significa "el commit anterior al actual", de modo que HEAD~2 apuntaría dos commits atrás. Así se puede retroceder varios pasos de una sola vez.

    Precaución con reset --hard

    git reset --hard es un comando destructivo e irreversible: además de mover el historial, borra del disco todo el trabajo no confirmado. Solo debe usarse cuando se está totalmente seguro de que esos cambios no se necesitan. Es el único de los tres reset que toca los archivos de forma que no se puede deshacer.

    Revertir un commit

    Si el commit que queremos deshacer ya se ha compartido con otros (por ejemplo, si ya se ha subido a GitHub), lo correcto no es "borrarlo" con reset, porque eso reescribiría el historial y descolocaría al resto del equipo. En su lugar, se crea un nuevo commit que revierte los efectos del anterior:

    git revert <id-del-commit>

    Este comando genera un commit nuevo que deshace exactamente lo que hizo el commit indicado, sin borrar nada del historial. De esta forma, todos los miembros del equipo siguen viendo la misma historia y nadie se descuadra. Es la forma "segura" de deshacer cuando el trabajo ya es público.

    Guardar cambios temporalmente

    Por último, existe una herramienta muy cómoda para guardar provisionalmente el trabajo sin hacer un commit: git stash. Sirve, por ejemplo, cuando nos interrumpen para resolver una urgencia y no queremos ni hacer un commit a medias ni perder lo que llevamos hecho:

    git stash

    Este comando guarda los cambios pendientes en una especie de "cajón" temporal y deja el directorio de trabajo limpio, como si no hubiéramos tocado nada. Cuando queramos recuperar ese trabajo:

    git stash pop

    que devuelve al directorio de trabajo los cambios guardados y los elimina del cajón. Es la manera de apartar trabajo a medias sin ensuciar el historial y sin arriesgarse a perderlo.

    Resumen de comandos

    Comando Descripción
    git init Crea un nuevo repositorio en la carpeta actual
    git status Muestra el estado de los archivos
    git add <archivo> Añade cambios a la zona de preparación
    git commit -m "mensaje" Confirma los cambios con un mensaje
    git log Muestra el historial de commits
    git diff Muestra las diferencias sin preparar
    git diff --staged Muestra las diferencias preparadas
    git branch <nombre> Crea una rama
    git switch <nombre> Cambia a una rama
    git switch -c <nombre> Crea una rama y cambia a ella
    git merge <nombre> Fusiona una rama con la actual
    git reset <archivo> Quita un archivo de la zona de preparación
    git checkout -- <archivo> Descarta los cambios de un archivo
    git reset --soft HEAD~1 Deshace el último commit conservando los cambios preparados
    git reset --mixed HEAD~1 Deshace el último commit dejando los cambios en el directorio
    git reset --hard HEAD~1 Deshace el último commit y elimina los cambios
    git revert <commit> Revierte un commit con otro nuevo
    git stash Guarda temporalmente los cambios pendientes
