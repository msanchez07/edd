    Introducción a Git

    Git es un sistema de control de versiones distribuido, gratuito y de código abierto, que permite registrar y gestionar todos los cambios que se producen en un proyecto a lo largo de su vida. Aunque a primera vista pueda parecer una herramienta más dentro del amplio catálogo que hemos repasado, Git se ha convertido en el estándar de facto de la industria del software: hoy en día, prácticamente cualquier proyecto serio lo utiliza, desde pequeñas aplicaciones personales hasta gigantes como el propio núcleo de Linux, del que nació.

    Para entender qué hace especial a Git, conviene recordar lo que ya vimos al hablar de los sistemas de control de versiones. Los sistemas más antiguos, como CVS o Subversion, eran centralizados: todas las versiones del proyecto se guardaban en un único servidor, y cada programador trabajaba con una copia parcial de la información. Esto planteaba un problema evidente: si el servidor fallaba, o si simplemente se perdía la conexión a la red, nadie podía trabajar ni consultar el historial. El proyecto dependía por completo de la salud de ese punto central.

    Git rompió con esa idea. Fue creado en 2005 por Linus Torvalds, el mismo creador del núcleo de Linux, precisamente para gestionar el desarrollo de ese proyecto. El kernel de Linux es desarrollado por miles de personas repartidas por todo el mundo, y para colmo con un flujo de trabajo muy especial: cada contribución llega en forma de parches que hay que integrar y probar sin detener el desarrollo. Los sistemas centralizados de la época no daban abasto para semejante escala, y las herramientas propietarias generaban desconfianza en una comunidad que valora el software libre. La solución que planteó Torvalds fue radical y brillante a la vez: en lugar de que exista una única copia "verdadera" en un servidor, cada desarrollador dispone de una copia completa de todo el repositorio, con todo su historial, en su propio equipo.

    Esto, que puede parecer un simple detalle técnico, tiene consecuencias enormes. Significa que cada copia local es, en sí misma, un repositorio completo y autosuficiente. Se puede trabajar sin conexión, hacer commits, consultar el historial, crear ramas... todo sin tocar el servidor ni depender de la red. Y, si el servidor central se estropeara por completo, cualquier copia local serviría para restaurarlo tal y como estaba. Esta es la esencia de los sistemas distribuidos que ya estudiamos en el apartado anterior, llevada a la práctica.

    El cambio de paradigma: instantáneas frente a diferencias

    Hay un segundo aspecto, más profundo y menos visible, que distingue a Git de casi todos los sistemas que le precedieron: cómo concibe y guarda la información. Este detalle explica por qué Git es tan rápido, tan fiable y tan flexible, así que merece la pena detenerse en él.

    La mayoría de los sistemas de control de versiones almacenan los cambios como una serie de diferencias (deltas) entre una versión y la siguiente. Es decir, guardan la primera versión completa de un archivo y, a partir de ahí, solo anotan lo que cambió: "en esta línea se borró una palabra", "aquí se añadieron tres caracteres", "allá se modificó un número". Para reconstruir la versión actual, el sistema tiene que ir aplicando esas diferencias una tras otra, como quien rehace un texto partiendo de la página original y de una lista de correcciones. Es un enfoque económico en espacio, porque solo se guarda lo que varía, pero obliga a mantener una cadena de reconstrucciones que se vuelve frágil cuando esa cadena es muy larga.

    Git dio un giro radical a esa idea. En lugar de pensar en diferencias, funciona como una cámara de fotos: cada vez que se confirma un cambio (lo que en Git se llama commit), se toma una instantánea completa del estado de todos los archivos del proyecto en ese momento. Cada commit es, por así decirlo, una fotografía entera del proyecto en un instante concreto, con todos sus archivos tal y como estaban.

    Esta característica es la que da sentido a la metáfora de la máquina del tiempo que usábamos al hablar del control de versiones: cada commit es una parada en el tiempo a la que se puede volver directamente, sin necesidad de recorrer todo el camino desde el principio. Para reconstruir cómo estaba el proyecto hace tres semanas, basta con consultar la instantánea de aquel día; no hay que aplicar diferencias una a una.

    Ahora bien, si cada commit guarda el proyecto entero, uno podría pensar que Git consume una cantidad de espacio desorbitada. La clave está en una optimización sencilla pero potentísima: si un archivo no ha cambiado entre dos instantáneas, Git no lo vuelve a copiar, sino que guarda una referencia al contenido que ya tiene almacenado. Es decir, las "fotos" comparten los elementos que permanecen iguales. Por eso, a pesar de guardar instantáneas completas, Git es extraordinariamente eficiente en cuanto a espacio y velocidad. Es el mejor de los dos mundos: la comodidad de tener siempre la foto completa y la ligereza de no duplicar lo que no cambia.

    Esa filosofía de las instantáneas explica también otras virtudes de Git. Las operaciones de comparación, de navegación por el historial y de cambio entre ramas son casi instantáneas, porque no hay que reconstruir nada: las fotos ya están allí, completas. Y, a diferencia de los sistemas basados en diferencias, donde perderse en medio de la cadena de reconstrucciones podía ser problemático, en Git cada punto del historial es autónomo y accesible por sí solo.

    Esta forma de trabajar es tan útil que merece la pena interiorizarla desde el principio. De la misma forma que un álbum de fotos permite volver a ver cómo era algo en el pasado, Git permite volver atrás en el tiempo y recuperar cualquier estado anterior del proyecto cuando se necesite. Y no solo eso: también dice quién hizo cada cambio, cuándo lo hizo y por qué (si se ha escrito un buen mensaje de commit). Ese conjunto de fotos fechadas y atribuidas es la memoria del proyecto, y es lo que convierte a Git en una herramienta tan valiosa como fuente de tranquilidad.

    ¿Por qué usar Git?

    Al principio puede parecer que Git es una complicación innecesaria, sobre todo cuando se trabaja en solitario y con proyectos pequeños. Sin embargo, las ventajas que aporta son tan importantes que pronto se convierte en una herramienta imprescindible. Conviene repasarlas con calma, porque cada una responde a un problema real:

    • Historial completo del proyecto. Git guarda un registro de absolutamente todo lo que ha ocurrido en el proyecto: qué archivos se han creado, modificado o borrado, quién lo hizo y cuándo. Cuando más adelante alguien se pregunte "¿por qué este código está aquí?" o "¿cuándo se introdujo este error?", el historial de Git tiene la respuesta. Basta con consultar el git log y navegar por los commits hasta dar con el cambio que se busca.
    • Posibilidad de volver atrás. Todos hemos sentido alguna vez ese temor de modificar un código que funciona y estropearlo sin remedio. Con Git ese miedo desaparece: si algo sale mal, siempre se puede volver a una versión anterior del archivo o del proyecto entero. Es una auténtica "máquina del tiempo" para el código, y su existencia anima a experimentar sin miedo.
    • Trabajo en paralelo. En los equipos de desarrollo, varias personas trabajan a la vez sobre los mismos archivos. Git permite que cada uno avance de forma independiente, gracias sobre todo a las ramas (branches), y luego integre sus cambios sin pisar el trabajo de los demás. Sin una herramienta así, coordinar a un equipo sería un caos de archivos enviados por correo con nombres como proyecto_final_v2_definitivo_bueno.java.
    • Seguridad. Al ser un sistema distribuido, cada copia local es una copia de seguridad completa del proyecto. Si se estropea un equipo o se borra el servidor remoto, el proyecto no se pierde: siempre queda una copia en otro sitio. Esta resiliencia es la que ya vimos como gran ventaja de los sistemas distribuidos.
    • Rapidez. Casi todas las operaciones de Git se ejecutan en local, sin necesidad de conexión a Internet. Comparar versiones, ver el historial o crear ramas es prácticamente instantáneo, aunque el proyecto sea enorme. Esto, que en sistemas centralizados suponía esperar al servidor, aquí se resuelve en milisegundos.
    • Trazabilidad y responsabilidad. En un proyecto real conviene saber quién ha tocado un determinado trozo de código, por si hay que preguntarle algo o simplemente para entender el contexto de un cambio. Git deja constancia del autor de cada modificación, lo que fomenta la transparencia y facilita la colaboración.

    Git frente a otros sistemas de control de versiones

    Para situar a Git, conviene compararlo con los sistemas que hemos visto anteriormente. Herramientas como CVS o Subversion son sistemas centralizados: hay un único repositorio en un servidor y los programadores se conectan a él para obtener y enviar cambios. Funcionan bien para equipos pequeños y proyectos poco complejos, pero dependen de la conexión al servidor y, si este falla, todo el trabajo colaborativo se detiene. Además, guardan los cambios como diferencias, lo que los hace más lentos en algunas operaciones.

    Git, en cambio, es distribuido y trabaja con instantáneas completas. Cada programador tiene una copia íntegra del repositorio en su máquina, lo que le da una independencia total respecto al servidor y una robustez muy superior. Es cierto que la curva de aprendizaje de Git es algo mayor, porque tiene más conceptos y comandos, y porque su modelo interno (las tres áreas, el índice, las ramas como punteros) no es tan intuitivo de primeras. Pero a cambio ofrece una potencia y una flexibilidad que los sistemas centralizados no pueden igualar. Hoy en día, la inmensa mayoría de proyectos nuevos se gestionan con Git, y GitHub, GitLab y Bitbucket, las principales plataformas de alojamiento de código, están construidas sobre él.

    Instalación de Git

    Git está disponible para los tres sistemas operativos principales. A continuación se describe el proceso de instalación en cada uno de ellos, pero antes de entrar en detalle conviene recordar una idea sencilla: sea cual sea el sistema, la instalación consiste básicamente en descargar el programa y asegurarse de que el comando git queda disponible en la terminal. El resto de la configuración es igual en todos los casos.

    Windows

    En Windows, la forma más sencilla y recomendada es descargar el instalador oficial, conocido como Git for Windows, desde la página git-scm.com. Se descarga el ejecutable y se lanza el asistente de instalación, aceptando las opciones por defecto. Aunque el instalador ofrece muchas opciones de configuración, para empezar no es necesario modificar nada: con los valores predeterminados Git queda perfectamente funcional.

    Junto con Git, se instala una herramienta muy útil llamada Git Bash: una terminal que permite ejecutar no solo los comandos de Git, sino también muchos comandos propios de los sistemas Linux. Es muy recomendable acostumbrarse a usar Git Bash (o cualquier otra terminal) para trabajar con Git, ya que la línea de comandos es la forma más directa y completa de aprovechar todas sus capacidades. Las interfaces gráficas son cómodas, pero esconden parte de lo que ocurre por debajo, y conviene entender la herramienta de verdad.

    Una vez finalizada la instalación, abrimos Git Bash y comprobamos que todo ha ido bien ejecutando:

    git --version

    Si el comando devuelve la versión de Git instalada (por ejemplo, git version 2.40.1), la instalación ha sido correcta. Ese sencillo chequeo sirve para confirmar que el comando se reconoce y que la instalación no se ha quedado a medias.

    Linux

    En Linux, la instalación es todavía más sencilla, ya que Git se encuentra en los repositorios oficiales de prácticamente todas las distribuciones. Basta con usar el gestor de paquetes habitual del sistema.

    En Debian, Ubuntu y derivadas, se ejecuta:

    sudo apt update
sudo apt install git

    En Fedora, CentOS y otras distribuciones basadas en RPM:

    sudo dnf install git

    En Arch Linux y derivadas:

    sudo pacman -S git

    Para comprobar que la instalación se ha realizado correctamente, se ejecuta el mismo comando que en Windows:

    git --version

    macOS

    En macOS existen dos formas habituales de instalar Git.

    La primera consiste en instalar las Command Line Tools de Xcode, que incluyen Git entre sus herramientas. Al ejecutar por primera vez un comando de Git, el sistema suele ofrecer automáticamente la instalación de estas herramientas; también se pueden instalar manualmente con:

    xcode-select --install

    La segunda opción, muy habitual entre desarrolladores, es utilizar el gestor de paquetes Homebrew. Si ya se tiene instalado, basta con ejecutar:

    brew install git

    En cualquiera de los dos casos, se comprueba la instalación con:

    git --version

    Configuración inicial de Git

    Antes de empezar a trabajar con Git es imprescindible realizar una configuración mínima. Git necesita saber, como mínimo, quién eres, porque esa información quedará asociada a cada uno de los commits que realices. Esto no es un capricho: cuando varias personas trabajan sobre el mismo código, saber quién hizo cada cambio es lo que permite entender el historial, localizar responsables y resolver dudas. Si Git no supiera quién eres, los commits quedarían huérfanos, sin autor, y el historial perdería buena parte de su valor.

    La jerarquía de niveles de configuración

    La configuración de Git se basa en pares de "clave = valor" y se gestiona con el comando git config. Lo interesante es que Git no tiene un único archivo de configuración, sino tres niveles que se aplican en cascada, de mayor a menor alcance. Conocerlos ayuda a entender dónde se guarda cada ajuste y por qué unos prevalecen sobre otros.

    • Nivel de sistema (--system): se aplica a todos los usuarios del equipo. Vive en un archivo de configuración del propio sistema operativo y, por tanto, para modificarlo hacen falta permisos de administrador. Se usa, por ejemplo, para definir ajustes comunes a toda una máquina compartida.
    • Nivel global (--global): se aplica a todos los repositorios de un mismo usuario. Corresponde a la configuración personal de cada desarrollador y es el nivel más habitual para ajustar el nombre, el correo o el editor. Es el que se modifica cuando alguien configura Git en su equipo por primera vez.
    • Nivel local (--local): se aplica únicamente al repositorio en el que nos encontremos. Es el nivel por defecto cuando no se indica ninguno y sirve para ajustes específicos de un proyecto concreto, como usar un correo diferente para el trabajo o un nombre distinto.

    La cascada funciona de modo que un nivel más específico pisa a uno más general: si un ajuste está definido a la vez en el nivel global y en el local, prevalece el local. Así, un desarrollador puede tener una configuración global para su día a día y, al mismo tiempo, sobrescribirla solo para un proyecto concreto sin afectar a los demás.

    Configurar la autoría

    Para configurar el nombre de usuario y el correo electrónico a nivel global, se ejecutan los siguientes comandos:

    git config --global user.name "Tu Nombre"
git config --global user.email "tu.correo@ejemplo.com"

    Es muy importante que el correo electrónico coincida con el que usaremos más adelante en GitHub, porque es el dato que la plataforma utiliza para asociar los commits con nuestra cuenta. Si el correo no coincide, GitHub no podrá reconocer nuestra autoría y los cambios aparecerán a nombre de nadie o de una cuenta distinta.

    Configuración mínima imprescindible

    Aunque Git funciona sin configuración previa, es obligatorio configurar user.name y user.email antes de realizar el primer commit. Si no se hace, Git mostrará un aviso y, en algunos casos, se negará directamente a crear el commit. Por eso, este paso debe ser siempre el primero al empezar a trabajar con Git en un equipo nuevo. No es una recomendación estética: sin autoría, el commit no tiene sentido.

    Otros ajustes útiles

    Además de estos dos datos básicos, conviene configurar el editor de texto que Git utilizará para abrir los mensajes de los commits y para resolver conflictos. Si usamos Visual Studio Code, el comando sería:

    git config --global core.editor "code --wait"

    En Windows también es recomendable configurar el manejo de los fines de línea, ya que Windows y Linux utilizan caracteres distintos para marcar el final de una línea. Si no se controla ese detalle, un mismo archivo puede aparecer como "modificado" en todos sus renglones sin que nadie haya tocado nada, lo que ensucia el historial de diffs. Para evitarlo, se puede indicar a Git que convierta automáticamente los fines de línea:

    git config --global core.autocrlf true

    Para comprobar la configuración que tenemos establecida, se puede ejecutar:

    git config --list

    Este comando muestra todas las opciones configuradas, tanto las que hemos establecido nosotros como las que Git trae por defecto. Es una buena forma de verificar que todo ha quedado como esperábamos antes de empezar a trabajar.
