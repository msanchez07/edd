📝 Tarea de Evaluación: Control de Versiones, Colaboración Remota e Integración Continua

UD 03 · Control de versiones

Esta tarea evalúa el bloque de control de versiones completo. El código apenas importa para superar la prueba: lo que se valora es cómo se organiza, se comparte y se verifica automáticamente ese código.

👤 Modalidad: Individual
📄 Formato: Repositorio en GitHub
🎙️ Defensa: Ampliación (1 hora) + Oral individual (3 a 5 minutos)
⚠️ Requisitos clave: la tarea se realiza con una sola cuenta de GitHub, pero reproduciendo igualmente los flujos colaborativos (ramas, Pull Requests, revisión y conflictos). Entregar la memoria es obligatorio para poder defender la tarea.

Escenario

La aplicación de inventario del taller

Vas a desarrollar una aplicación Java de consola para llevar el inventario de un taller. El punto de partida es esta clase, que deberá vivir dentro de un proyecto Java: 

public class Inventario {
    public static void main(String[] args) {
        int unidades = 10;
        System.out.println("Unidades en inventario: " + unidades);
    }
}

A partir de ahí, debes demostrar que sabes llevar el control de versiones del proyecto, trabajar con un repositorio remoto y verificar el código de forma automática. Los tres primeros bloques son guiados y consecutivos: cada uno se apoya en lo construido en el anterior. Al final hay una ampliación sin pasos, donde tendrás que aplicar lo aprendido por tu cuenta.

Qué se pide

Bloques de trabajo

🅰️ Bloque A. Control de versiones integrado en el IDE

El objetivo es demostrar que sabes realizar el control de versiones desde el propio entorno de desarrollo, y no solo escribiendo comandos en la terminal. Muchas operaciones tienen un comando equivalente, pero aquí se evalúa el uso de la interfaz de IntelliJ.

  • Crea el proyecto Java en IntelliJ con la clase Inventario y activa el control de versiones desde Git → Create Git Repository (o VCS → Enable Version Control Integration...).
  • Crea antes del primer commit un archivo .gitignore que evite versionar los archivos generados por el IDE y la compilación: al menos out/, .idea/, *.iml y *.class.
  • Realiza al menos tres commits con mensajes significativos desde el panel Commit, seleccionando los archivos con las casillas de verificación. Modifica el Inventario entre commit y commit: por ejemplo, añade un método nuevo en el segundo y una mejora de la salida por consola en el tercero.
  • Comprueba que entiendes el código de colores del IDE (rojo para untracked, verde para staged y azul para modified) y déjalo por escrito en la memoria.
  • Crea desde la interfaz una rama llamada feature/salida-mejorada, realiza en ella al menos un commit, vuelve a main y fusíonala desde IntelliJ. El historial debe quedar limpio y comprensible.

Evidencias para la memoria: capturas del panel Commit mostrando el staging por casillas, del árbol del proyecto con los colores de estado, del historial de commits y del momento de crear o fusionar la rama.

🅱️ Bloque B. Repositorio remoto y colaboración

El objetivo es trasladar el proyecto a GitHub y trabajar con el flujo colaborativo propio de un repositorio remoto.

  • Crea un repositorio en GitHub, vincúlalo con tu repositorio local como remoto origin y sube la rama main.
  • El trabajo colaborativo se reproduce con el flujo de rama y Pull Request. Crea una rama nueva (por ejemplo feature/contador-unidades), realiza en ella al menos un commit, súbela a GitHub y abre un Pull Request describiendo qué has hecho y por qué.
  • Añade en la conversación del Pull Request al menos un comentario de autorrevisión señalando una mejora o un aspecto a revisar del cambio, y atiende las observaciones que el profesor pueda dejar antes de fusionarlo.
  • Provoca un conflicto tú mismo: crea dos ramas a partir de main y modifica en ambas la misma línea de Inventario.java, pero de forma distinta. Fusiona una sobre main y después la otra, resuelve el conflicto desde el editor de IntelliJ, prepáralo y cierra la fusión con un commit. Documenta en la memoria qué marcas encontraste y cómo decidiste la solución.
  • Practica la sincronización con el remoto usando Git → Update Project... (el equivalente a git pull), comprobando el estado del proyecto antes de continuar.

Evidencias para la memoria: enlace al repositorio, enlace al Pull Request con la autorrevisión, captura del conflicto antes y después de resolverlo, y descripción del flujo seguido.

🅲 Bloque C. Integración continua

El último bloque evalúa el uso de herramientas de integración continua, en este caso GitHub Actions.

  • Crea en la raíz del repositorio la carpeta .github/workflows/ y, dentro, un archivo ci.yml que se dispare con cada push y realice tres cosas: descargar el repositorio con actions/checkout, preparar un JDK con actions/setup-java y compilar el programa con javac Inventario.java.
  • Consigue una ejecución en verde y captura la pantalla de la pestaña Actions.
  • Provoca un fallo a propósito: borra un punto y coma del código, sube el cambio y observa cómo la ejecución se marca en rojo. Entra en los logs, localiza el mensaje de error del compilador, anota la línea que señala y corrige el código hasta volver al verde.
  • Ten en cuenta que javac Inventario.java funciona porque el archivo está en la raíz del repositorio. Si mueves la clase a una carpeta src/, el comando del flujo debe actualizarse en consonancia para evitar el error file not found.

Evidencias para la memoria: captura de la ejecución en verde, captura de la ejecución en rojo con el log del error visible y explicación de cómo se corrigió.
