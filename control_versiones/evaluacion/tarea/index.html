    Tarea de evaluación: control de versiones, colaboración remota e integración continua

    Esta tarea evalúa el bloque de control de versiones completo y se corresponde con los criterios de evaluación 4.f, 4.h y 4.i del módulo profesional 0487 (Entornos de desarrollo):

    • 4.f Se ha realizado el control de versiones integrado en el entorno de desarrollo.
    • 4.h Se han utilizado repositorios remotos para el desarrollo de código colaborativo.
    • 4.i Se han utilizado herramientas para la integración continua del código.

    El código apenas importa para superar la prueba: lo que se valora es cómo se organiza, se comparte y se verifica automáticamente ese código.

    Condiciones de la prueba

    • Modalidad: individual. La tarea se realiza con una sola cuenta de GitHub, pero se reproducen igualmente los flujos de trabajo colaborativos (ramas, Pull Requests, revisión y resolución de conflictos) que son los que evalúa el criterio 4.h.
    • Entregables:
      • Enlace al repositorio en GitHub (público o compartido con el docente).
      • Memoria técnica en PDF (máximo 4 páginas) con las evidencias y las justificaciones que se piden en cada bloque.
      • Defensa oral individual de 3 a 5 minutos.
    • Calificación: 10 puntos, repartidos en 6 puntos para los bloques guiados (2 puntos por bloque) y 4 puntos para la ampliación final. Entregar la memoria es obligatorio para poder defender la tarea.
    • Herramienta principal: IntelliJ IDEA con el control de versiones integrado y una cuenta de GitHub.

    El escenario: la aplicación de inventario del taller

    Vas a desarrollar una aplicación Java de consola para llevar el inventario de un taller. El punto de partida es esta clase, que deberá vivir dentro de un proyecto Java:

    public class Inventario {
    public static void main(String[] args) {
        int unidades = 10;
        System.out.println("Unidades en inventario: " + unidades);
    }
}

    A partir de ahí, debes demostrar que sabes llevar el control de versiones del proyecto, trabajar con un repositorio remoto y verificar el código de forma automática. Los tres primeros bloques son guiados y consecutivos: cada uno se apoya en lo construido en el anterior. Al final hay una ampliación sin pasos, donde tendrás que aplicar lo aprendido por tu cuenta.

    Bloque A. Control de versiones integrado en el IDE (criterio 4.f)

    El objetivo de este bloque es demostrar que sabes realizar el control de versiones desde el propio entorno de desarrollo, y no solo escribiendo comandos en la terminal. Muchas de las operaciones tienen un comando equivalente, pero lo que se evalúa aquí es el uso de la interfaz de IntelliJ.

    Para empezar, crea el proyecto Java en IntelliJ con la clase Inventario y activa el control de versiones desde el menú Git → Create Git Repository (o VCS → Enable Version Control Integration...). A continuación, crea antes del primer commit un archivo .gitignore que evite versionar los archivos generados por el IDE y la compilación: al menos out/, .idea/, *.iml y *.class.

    Una vez inicializado el repositorio, realiza al menos tres commits con mensajes significativos desde el panel Commit, seleccionando los archivos mediante las casillas de verificación. Aprovecha para modificar el Inventario entre commit y commit: por ejemplo, añade un método nuevo en el segundo y una pequeña mejora de salida por consola en el tercero. Comprueba que entiendes el código de colores que muestra el IDE (rojo para untracked, verde para staged y azul para modified) y deja constancia de ello en la memoria.

    El siguiente paso es trabajar con ramas. Crea desde la interfaz una rama llamada feature/salida-mejorada, realiza en ella al menos un commit, y vuelve a main. Fusiona la rama con la principal desde IntelliJ y comprueba el resultado en el historial gráfico del IDE. El histórico debe quedar limpio y comprensible.

    Evidencias para la memoria: capturas del panel Commit mostrando el staging por casillas, del árbol del proyecto con los colores de estado, del historial de commits y del momento de crear o fusionar la rama.

    Bloque B. Repositorio remoto y colaboración (criterio 4.h)

    A partir de esta base, el objetivo es trasladar el proyecto a GitHub y trabajar con el flujo colaborativo propio de un repositorio remoto, que es lo que pide el criterio 4.h. Crea un repositorio en GitHub, vincúlalo con tu repositorio local como remoto origin y sube la rama main.

    El trabajo colaborativo se reproduce con el flujo de rama y Pull Request, el mismo que se usa en cualquier equipo. Crea una rama nueva (por ejemplo feature/contador-unidades), realiza en ella al menos un commit, súbela a GitHub y abre un Pull Request describiendo qué has hecho y por qué. Añade en la conversación del Pull Request al menos un comentario de autorrevisión señalando una mejora o un aspecto a revisar del cambio, y atiende las observaciones que el profesor pueda dejar en él antes de fusionarlo.

    Para evaluar la resolución de conflictos no hace falta otra persona: puedes provocar uno tú mismo. Crea dos ramas a partir de main y modifica en ambas la misma línea de Inventario.java, pero de forma distinta. Fusiona una sobre main y después la otra: Git avisará del conflicto. Resuélvelo desde el editor de IntelliJ, dejando el archivo en su versión definitiva, prepáralo y cierra la fusión con un commit. Documenta en la memoria qué marcas encontraste y cómo decidiste la solución.

    A lo largo de este bloque, practica también la sincronización con el remoto usando Git → Update Project... (el equivalente a git pull), comprobando el estado del proyecto antes de continuar.

    Evidencias para la memoria: enlace al repositorio, enlace al Pull Request con la autorrevisión, captura del conflicto antes y después de resolverlo, y descripción del flujo seguido.

    Bloque C. Integración continua (criterio 4.i)

    El último bloque evalúa el uso de herramientas de integración continua, en este caso GitHub Actions. Crea en la raíz del repositorio la carpeta .github/workflows/ y, dentro, un archivo ci.yml que se dispare con cada push y realice tres cosas: descargar el repositorio con actions/checkout, preparar un JDK con actions/setup-java y compilar el programa con javac Inventario.java.

    Una vez subido el flujo, consigue una ejecución en verde y captura la pantalla de la pestaña Actions. Después, provoca un fallo a propósito: borra un punto y coma del código, sube el cambio y observa cómo la ejecución se marca en rojo. Entra en los logs, localiza el mensaje de error del compilador, anota la línea que señala y finalmente corrige el código y confirma que la ejecución vuelve al verde.

    Ten en cuenta un detalle que suele dar problemas al trasladar esto a proyectos reales: el comando javac Inventario.java funciona porque el archivo está en la raíz del repositorio. Si mueves la clase a una carpeta src/, el comando del flujo debe actualizarse en consonancia para evitar el error file not found.

    Evidencias para la memoria: captura de la ejecución en verde, captura de la ejecución en rojo con el log del error visible y explicación de cómo se corrigió.

    Bloque D. Ampliación sin pasos

    Aquí no hay comandos ni rutas indicadas: se trata de que resuelvas por tu cuenta, con lo aprendido en los bloques anteriores. Se evalúa tu capacidad de aplicar las mismas herramientas a situaciones que no vienen descritas paso a paso.

    D1. Intervenir sobre el historial (4.f)

    Deja el historial del repositorio en un estado limpio y corregido:

    • Deshaz el último commit sobre Inventario.java conservando sus cambios, para poder volver a confirmarlos con un mensaje mejor.
    • Provoca a propósito un reset que haga "desaparecer" un commit y recupéralo después. Deja constancia de cómo lo has localizado.
    • Incorpora a main una funcionalidad nueva (por ejemplo, que el número de unidades se lea de args[0]) repartida en al menos dos commits atómicos con mensajes correctos.

    D2. El remoto va por delante (4.h)

    Otra persona (un compañero, el profesor, o tú mismo desde una segunda rama que simula a otra cuenta) ha subido un cambio al repositorio remoto después de tu último envío, y otro cambio toca Inventario.java en líneas distintas de las tuyas.

    • Trae los cambios del remoto antes de volver a subir.
    • Intenta subir tu trabajo sin haber integrado antes y observa qué ocurre.
    • Fusiona ambas líneas de trabajo resolviendo el conflicto sin perder ni tu cambio ni el ajeno. Documenta el orden de operaciones y por qué.

    D3. Ampliar el flujo de integración continua (4.i)

    Modifica el flujo para que, además de compilar el programa:

    • Lo ejecute en el runner y deje ver su salida por consola.
    • Marque la ejecución en rojo también cuando el programa termine con error, no solo cuando no compile.

    Para subir nota, puedes además hacer que el flujo se dispare en pull_request o que se ejecute en dos sistemas operativos distintos.

    Evidencias para la memoria: capturas de las ejecuciones del flujo ampliado en verde y en rojo, el historial antes y después de las operaciones sobre commits, y explicación del orden seguido en la integración con el remoto.
